# Large and hard engineering projects in saleor/apps and the Saleor app ecosystem (state as of 2026-11-13)

Method and caveats (apply to every section):

- Primary evidence is a full local clone of `saleor/apps` (main at `f001ac7e`, 2026-10-28, 1,494 commits), `saleor/app-sdk` (main at 2026-11-05, v1.17.0), `saleor/saleor-app-payment-stripe` (last commit 2025-05-27) and `saleor/saleor-app-template` (2026-11-04). PR titles, dates, squash-commit bodies, changeset texts and CHANGELOG entries were read from git.
- Sizes are `git --numstat` of the squash commit on main, **excluding** `pnpm-lock.yaml`, `generated/`, `schema.graphql`, `graphql.schema.json` and `*.snap`. Format: `[files, +added, -deleted]`. They are therefore smaller than GitHub's "+/-" numbers.
- The GitHub REST API was rate-limited from this machine, so per-PR commit counts, review-comment counts and open-to-merge durations were **not retrieved**. Durations given are first-to-last merge dates of a PR sequence.
- PR links follow `https://github.com/saleor/apps/pull/<n>`; they were derived from the `(#n)` suffix of squash commits, not individually opened in a browser.
- Since 2026-09-17 the public repo receives bot commits titled "Sync from internal repository (N changes) (#k)". The `#k` numbers (8 to 150) are far below the public PR counter (last public PR #2443), so they almost certainly refer to an internal repository; **unconfirmed**. For that period I cite commit hashes and CHANGELOG entries, not PRs.
- Licences (read from each repo's `LICENSE`): `saleor/apps` BSD-3-Clause; `saleor/app-sdk` BSD-3-Clause; `saleor/saleor-app-payment-stripe` BSD-3-Clause; `saleor/saleor-app-template` BSD-3-Clause. `saleor/saleor-app-payment-adyen` was not checked.
- No source code is copied below; a few changeset sentences are quoted as evidence.

## Stripe app: rewrite from legacy payment-stripe to apps/stripe, async results, idempotency, duplicate/out-of-order events, refunds, cancellations, multi-channel config, API versions, merchant migration

### Takeaway
The new Stripe app was a from-scratch build, not a port: 104 non-trivial PRs between 2025-04-02 and 2025-06-23 (about +32k/-9k lines), followed by 18 months of hardening that is almost entirely about cross-system failure modes (duplicate requests, Saleor retries, events from other environments, orphaned PaymentIntents, version-gated payloads). No merchant-migration tooling from the legacy app was found; the legacy repo is simply marked deprecated.

Post-launch hardening (what broke)
- Events not created by the app: "Drop events not created by Saleor" [#2035](https://github.com/saleor/apps/pull/2035) 2025-07-24 [30f +262 -32]. Changeset: "Events from Stripe that doesn't contain metadata are now gracefully ignored. App will not try to proceed such event, which eventually ended with TransactionNotFound error." The PR also had to start setting metadata on refund creation.
- Events from another installation: "Reject stripe events not created by proper app" [#2239](https://github.com/saleor/apps/pull/2239) 2026-02-23: "Verify if webhooks are connected to the original app installation that executed the payment intent".
- That fix then caused a Stripe-side incident pattern, fixed in v2.11.3 (synced 2026-10-13, commit [`205859ef`](https://github.com/saleor/apps/commit/205859ef)): "Before: the app answered these events with HTTP 400. Stripe kept retrying them for up to 3 days, sent 'having trouble delivering webhooks' emails, and could eventually disable the endpoint. After: the app acknowledges these events with HTTP 200 and ignores them." It also raises an App Problem recommending a separate Stripe account per environment — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Concurrent duplicates: "Make DynamoDB writer handle idempotency correctly" [#2181](https://github.com/saleor/apps/pull/2181) 2025-12-23: "Fixed race condition in transaction recording that caused `ConditionalCheckFailedException` errors. Previously, when two concurrent requests with the same idempotency key arrived (e.g., user clicking pay button multiple times), the second request would fail with a DynamoDB error. Now, duplicate write attempts are treated as idempotent success".
- Orphaned intents: "Stripe: Cancel orphaned Payment Intents on initialize session failure" [#2208](https://github.com/saleor/apps/pull/2208) 2026-01-27: "Now app will cancel Payment Intent (on Stripe side) when it fails to finish saving transaction on app's side (record in DynamoDB). That behavior was partially broken and webhooks couldn't be resolved."
- Saleor retries causing double refunds, fixed in the release synced 2026-09-29 (commit [`a3c91997`](https://github.com/saleor/apps/commit/a3c91997), changeset 57acbeb): "Refunds, captures and cancellations are no longer performed twice when Saleor re-delivers the same request. Saleor retries a transaction action webhook up to five times when the app is slow or returns an error, and until now each retry reached Stripe as a brand new call - a retry that arrived after Stripe had already accepted a refund created a second, duplicate refund. The app now forwards the `idempotencyKey` that Saleor sends with the request ... Requires Saleor 3.23 or newer". The same release line records "Dropped support for Saleor 3.22" (changeset b5f3231) — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Out-of-order arrival: changeset d3e9a93: "Fixed payment method details ... missing on transactions for Saleor 3.23 and newer. Before, the Stripe webhook sent payment method details only on Saleor 3.22. If the Stripe webhook arrived before the shopper returned to the storefront, or Saleor completed the checkout itself, the transaction had no payment method." — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Duplicate reports to core are tolerated: the Stripe-webhook use case treats core's "already reported" answer to `transactionEventReport` as success (class `TransactionEventReporter.AlreadyReportedError`) — [transaction-event-reporter.ts](https://github.com/saleor/apps/blob/main/apps/stripe/src/modules/saleor/transaction-event-reporter.ts)

- App Problems reporting: [#2255](https://github.com/saleor/apps/pull/2255) 2026-02-25 [35f +1457 -1].

### Inferences
- The hard part was never a single PR. Four areas were each rewritten within days of first landing (webhook keyed by channel then by config; process-session; Stripe event handling; Saleor response shapes), which is the signature of a contract being discovered rather than implemented.
- The best benchmark seeds are the post-launch defects, because each has a small diff but needs reasoning across three parties (core retry policy, app store, provider): duplicate refund on retry, concurrent initialize race, orphaned intent after store failure, foreign-environment events answered 400, payment-method details lost when the provider webhook wins the race.
- 3DS/requires-action is handled through the process-session flow and `amount_capturable_updated`/authorization PRs; no PR is titled for 3DS specifically.

### Gaps
- No tooling, script or documentation for migrating merchants from the legacy app or the old Stripe plugin to `apps/stripe` was found in either repo or on the docs overview page. The legacy repo was deprecated in place.
- No Stripe API version upgrade project was found after the freeze in #1933; the SDK pin is unchanged at HEAD.
- The specific Stripe changes inside the September to October 2026 sync commits cannot be attributed to individual public PRs.
- No public incident post-mortems were found; "what broke" is reconstructed from changesets.

## App SDK and platform: breaking changes, APL changes, JWS/HMAC, manifest and permissions, requiredSaleorVersion, webhook migration tooling, multi-version compatibility

### Takeaway
The platform-level work that crosses the app/core boundary is (1) the webhook-migration runner that rewrites installed apps' webhooks for every tenant at deploy time, with a documented history of reverts and one bug that disabled tenants' webhooks; (2) the APL move from Saleor Cloud APL to DynamoDB; (3) app-sdk 1.0; and (4) a steady cadence of dropping core versions. ## What made each hard: incidents, follow-ups, reverts, migrations, behaviour under retries and timeouts

### Takeaway
The recurring difficulty is disagreement about HTTP status semantics and redelivery between three parties, plus state that outlives the code version that wrote it. Explicit reverts are few but telling.

### Cited Findings
- Status code as control signal toward core: 4xx used to mean "do not retry", but with core's circuit breaker some errors must become 202 — [#2136](https://github.com/saleor/apps/pull/2136). Timeout maps to 504 — [#2279](https://github.com/saleor/apps/pull/2279). Unconfigured app keeps returning 400 but logs a warning — [apps CHANGELOG, 2026-09-29 sync](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Status code as control signal toward the provider: answering 400 to foreign Stripe events led to three days of retries and risk of the endpoint being disabled — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Redelivery: core retries transaction action webhooks up to five times; without a forwarded key each retry was a new refund — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Partial failure between store and provider: orphaned PaymentIntent when the DynamoDB write fails — [#2208](https://github.com/saleor/apps/pull/2208); concurrent identical initialize requests — [#2181](https://github.com/saleor/apps/pull/2181).
- Hanging handler instead of error response — [#1442](https://github.com/saleor/apps/pull/1442); unbounded settings fetch — [#1525](https://github.com/saleor/apps/pull/1525); an extra GraphQL call inside a sync webhook causing timeouts — [#1265](https://github.com/saleor/apps/pull/1265).
- Background work cut off by the serverless runtime: waitUntil revert [#1432](https://github.com/saleor/apps/pull/1432); client-log and exemption-metadata writes in the September to October 2026 syncs — [apps/avatax/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/avatax/CHANGELOG.md)
- Reverts: [#2104](https://github.com/saleor/apps/pull/2104) (feature plus two fixes), [#1582](https://github.com/saleor/apps/pull/1582) (migration exit code), [#1570](https://github.com/saleor/apps/pull/1570) (parallel migration), [#1432](https://github.com/saleor/apps/pull/1432), [#2213](https://github.com/saleor/apps/pull/2213) (DynamoDB deps), "Fix sentry sourcemaps by reverting sharing sentry init" [#1415](https://github.com/saleor/apps/pull/1415) [58f].
- Migrations: settings schema v1 to v2 [#535](https://github.com/saleor/apps/pull/535); metadata key rename `externalId` to `avataxId` [#826](https://github.com/saleor/apps/pull/826); webhook set changes at deploy [#1318](https://github.com/saleor/apps/pull/1318); stored `saleorSchemaVersion` rows [#2433](https://github.com/saleor/apps/pull/2433); permission grant on existing installs (Stripe v2.15.0) — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Silent failures: SMTP returning 200 for an unmapped notify sub-event [#2357](https://github.com/saleor/apps/pull/2357); SMTP webhooks not registered on 3.22 [#2442](https://github.com/saleor/apps/pull/2442); unknown AvaTax errors logged only as warnings — [apps/avatax/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/avatax/CHANGELOG.md)
- Numeric edge cases: non-zero rate with zero tax [#1726](https://github.com/saleor/apps/pull/1726); decimal places [#1527](https://github.com/saleor/apps/pull/1527); exemption sums moved to Decimal.js [#2183](https://github.com/saleor/apps/pull/2183); 20-character document code limit [#826](https://github.com/saleor/apps/pull/826).

### Inferences
- A benchmark task built from these should plant the failure in the interaction (redelivery, race, version skew, provider status semantics), not in a single handler; otherwise it reduces to an ordinary ticket.

### Gaps
- No customer-facing incident reports or status-page entries were searched for or found; severity and duration of each incident are unknown.

## Which have outcomes an end-to-end test could check from outside

### Takeaway
Nearly all top candidates have black-box observables at three points: what core receives back from a sync webhook or mutation, what the provider stub receives, and what the app persisted. The upstream repo itself tests this way (AvaTax e2e against a live Saleor, Stripe integration tests per flow, Mailpit for SMTP).

### Cited Findings
- Upstream harness evidence: `apps/avatax/e2e` holds 18 test files and 28 GraphQL documents (checkout and order flows, discounts, draft orders, tax-included products) — [apps/avatax/e2e](https://github.com/saleor/apps/tree/main/apps/avatax/e2e); Stripe has one integration-test PR per flow ([#1967](https://github.com/saleor/apps/pull/1967), [#1971](https://github.com/saleor/apps/pull/1971), [#1973](https://github.com/saleor/apps/pull/1973), [#1975](https://github.com/saleor/apps/pull/1975), [#1984](https://github.com/saleor/apps/pull/1984)) and an e2e checkout test — [apps/stripe/e2e](https://github.com/saleor/apps/tree/main/apps/stripe/e2e); SMTP added Mailpit in [#2091](https://github.com/saleor/apps/pull/2091) and password-event e2e in [#2359](https://github.com/saleor/apps/pull/2359); a payment test client app exists at `apps/payment-apps-testclient` — [apps folder](https://github.com/saleor/apps/tree/main/apps)
- Stripe duplicate refund on redelivery: observable as the number of refund calls and idempotency keys at the provider stub, and one refund event on the core transaction — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Stripe concurrent initialize: both responses succeed, one PaymentIntent, one stored record — [#2181](https://github.com/saleor/apps/pull/2181)
- Stripe orphaned intent: with the store failing, the provider stub receives a cancel and core receives a failure result — [#2208](https://github.com/saleor/apps/pull/2208)
- Stripe foreign or metadata-less events: HTTP 200 to the provider, no `transactionEventReport` to core, optional App Problem in core — [#2035](https://github.com/saleor/apps/pull/2035), [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- Stripe provider-webhook-before-return ordering: payment method details present on the core transaction either way — [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)
- AvaTax discounts: request body at the provider stub (`discounted` flags, discount total, shipping amount reduced) and line/shipping net, gross and rate returned to core, for calculate versus confirm — [#1552](https://github.com/saleor/apps/pull/1552), [#1522](https://github.com/saleor/apps/pull/1522)
- AvaTax commit and void: committed document at the stub on order confirmed, `avataxId` in order metadata, void on cancel, tolerated "not found" and "already cancelled", no error for non-AvaTax orders — [#826](https://github.com/saleor/apps/pull/826), [#1293](https://github.com/saleor/apps/pull/1293), [#1573](https://github.com/saleor/apps/pull/1573), [#1596](https://github.com/saleor/apps/pull/1596)
- AvaTax outage: status code core receives (504 on provider timeout, 202 versus 4xx versus 5xx classes) — [#2279](https://github.com/saleor/apps/pull/2279), [#2136](https://github.com/saleor/apps/pull/2136)
- AvaTax exemption: zero rate when taxable amount is zero; exemption status in checkout metadata — [#1726](https://github.com/saleor/apps/pull/1726), [#2183](https://github.com/saleor/apps/pull/2183)
- AvaTax client logs: stored log documents per checkout/order with TTL — [#1576](https://github.com/saleor/apps/pull/1576)
- SMTP: emails in an outbox for each event; count of registered webhooks in core after install on each supported core version; set-password email after `customerCreate` — [#2442](https://github.com/saleor/apps/pull/2442), [#2357](https://github.com/saleor/apps/pull/2357)
- Webhook migration: after deploy, each tenant's webhooks in core equal the manifest (names, queries, active flag), unreachable tenants are skipped, none left disabled — [#1717](https://github.com/saleor/apps/pull/1717), [#1637](https://github.com/saleor/apps/pull/1637)
- APL migration: app keeps authenticating to every tenant after the storage switch; unsupported APL value fails at start — [#2204](https://github.com/saleor/apps/pull/2204), [apps/stripe/CHANGELOG.md](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md)

### Inferences
- For a ten-service mirror, the highest-yield composite task is: add a payload field that exists only in the newer core schema, keep the older core working, migrate installed tenants' webhooks, and stay correct under redelivery. It combines the SMTP 3.22 incident, the webhook runner and the Stripe idempotency fix, and every part is checkable from outside.
- Purely internal work (DDD refactors, logging, UI, Next.js upgrades) is large by line count but has no external observable and should be excluded.

### Gaps
- Whether the upstream e2e suites assert on provider-side requests (rather than only on core's responses) was not verified file by file.
