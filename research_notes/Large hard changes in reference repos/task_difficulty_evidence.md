# Task difficulty evidence: what makes software tasks hard for frontier coding agents, and how benchmarks build large, long-horizon tasks (state as of 13 Nov 2026)

Conventions used in these notes:
- Every number carries the date of its source. Anything dated before about Nov 2025 is flagged "(older than 12 months, possibly outdated)".
- "Unconfirmed" means I only saw the number in an aggregator, a search-result summary, or a secondary write-up, not in the paper or official leaderboard.
- Numbers from paper pages were extracted by an automated page reader. Where the reader said a value came from a figure or was ambiguous, that is noted.
- Model names such as Claude Opus 5 / 5.5, Fable 5, GPT-5.5, GPT-5.6 Sol, Kimi K3 appear as the sources give them.

## 1. Which benchmarks target large or long-horizon software work, and what are their task sizes and current top scores?

### Takeaway
Benchmarks whose tasks are "one issue, a few files" (SWE-bench Verified, and increasingly SWE-bench Pro and Terminal-Bench 2.0) are at or near saturation in vendor-reported numbers by late 2026. The benchmarks still under about 50% share three traits: very large required output (hundreds to 100k+ lines: FeatureBench, SWE-EVO, SWE-Marathon, hardest ProgramBench tasks), diagnosis in a live noisy system with no pointer to the fault (ORCA-bench, ITBench-AA, DBA-Bench, SREGym "new failures"), or grading that goes beyond tests passing (Senior SWE-bench "tasteful" score, DBA-Bench Safe Pass, SWE-CI zero-regression rate).

SWE-bench Pro
- 1,865 tasks: 731 public (11 repos), 276 commercial (18 proprietary startup repos), 858 held-out (12 repos). Gold patches average 107.4 lines across 4.1 files; every task changes at least 10 lines and more than 100 tasks need over 100 lines. Languages Python, JavaScript, TypeScript, Go. — [SWE-Bench Pro paper, arXiv 2509.16941v2, 14 Nov 2025](https://arxiv.org/html/2509.16941v2)
- Paper scores (models as of 18 Sep 2025; older than 12 months): public set Claude Sonnet 4.5 43.6%, Claude Sonnet 4 42.7%, GPT-5 (high) 41.8%; commercial set Claude Opus 4.1 17.8%, GPT-5 (high) 15.7%. With a 50-turn, $2 cap: GPT-5 (high) 25.9%, Claude Opus 4.1 22.7%. — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2)
- Late-2026 numbers are aggregator-only and conflict. One tracker (27 Oct 2026) lists Claude Opus 5.5 at 89.9%, Claude Sonnet 5.5 at 81.3%, Claude Fable 5.1 at 81.2% (vendor-reported, mixed harnesses). A page dated 14 Sep 2026 gives the Scale SEAL standardised public-set leader as Muse Spark 1.1 at 61.5% and GPT-5.4 (xHigh) at 59.1%. All unconfirmed against labs.scale.com. — [BenchLM SWE-bench Pro](https://benchlm.ai/benchmarks/swe-bench-pro); [Morph SWE-Bench Pro page](https://www.morphllm.com/swe-bench-pro)
- SWE-Bench Pro Verified (Sep 2026) found two defects in SWE-bench Pro: agents could recover gold patches or hidden tests from git history, local files, or the network, and some task statements or tests were wrong. For GLM-5.2 the score fell from 78.80% to 57.32% (21.48 points) once anti-hacking controls were applied; local answer leakage was seen in at least 103 tasks and network leakage in 49. 119 candidate instances were reviewed, 102 revised (92 of them in the requirements text, only 17 in the hidden tests). — [SWE-Bench Pro Verified, arXiv 2609.08149](https://huggingface.co/papers/2609.08149.md)

SWE-EVO (release-level evolution)
- 48 tasks from 7 mature Python projects (scikit-learn, pydantic, dvc, dask and others); the agent gets release notes (optionally with PR and issue text) and must move the code base from one release tag to the next. Gold patch mean 610.5 lines, 20.9 files, 51.0 functions (max 4,113 lines, 105 files, 379 functions). Mean 874.0 tests per task of which 81.4 fail-to-pass. — [SWE-EVO, arXiv 2512.18470v2, 23 Dec 2025](https://arxiv.org/html/2512.18470v2)
- Best resolved rate: GPT-5 (medium) 20.83% with SWE-agent and 18.75% with OpenHands, versus 65.0% for the same model on SWE-bench Verified. Fix Rate (partial credit) 31.44% and 27.64%. With release notes only (no PR or issue text), GPT-5 drops to 16.67% (SWE-agent) and 14.58% (OpenHands). No Anthropic or Google model was evaluated. — [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2)
- A search summary says a later version reports GPT-5.4 with OpenHands at 25%; I did not see this in the fetched v2 text (unconfirmed). — [arXiv 2512.18470 listing](https://arxiv.org/abs/2512.18470?context=cs)

FeatureBench and FeatBench (feature implementation)
- FeatureBench: 200 tasks from 24 Python repos, built automatically by tracing unit tests along a function dependency graph so one task can span several commits and PRs. Filters: over 100 lines to implement, at least 10 fail-to-pass test points. Level 1 (feature removed from an otherwise intact repo) averages 790.2 lines, 15.7 files, 29.2 functions, against 32.8 lines, 1.7 files, 3 functions for SWE-bench. 62.7 fail-to-pass test points per task (SWE-bench 9.1). Problem statements average 4,818 words. Level 2 removes the repo and gives only the interface. — [FeatureBench, arXiv 2602.10975v1, 11 Feb 2026](https://arxiv.org/html/2602.10975v1)
- FeatureBench scores (Feb 2026), percentage of tests passed / percentage of tasks resolved: Codex + GPT-5.1-Codex 41.66 / 12.5; Claude Code + Claude Opus 4.5 43.29 / 11.0; OpenHands + Claude Opus 4.5 45.53 / 10.5; Gemini-CLI + Gemini 3 Pro 32.43 / 5.0. Token use per task 2.0M–8.1M input. The same Opus 4.5 scores 74.4% on SWE-bench Verified. — [arXiv 2602.10975v1](https://arxiv.org/html/2602.10975v1); [arXiv abstract](https://arxiv.org/abs/2602.10975)
- FeatBench: 157 tasks from 27 repos, natural-language-only feature requests with no code hints; best configuration resolved 29.94% (older than 12 months for the preprint; journal version Feb 2026). Reports "scope creep", where agents implement aggressively beyond the request. — [FeatBench, arXiv 2509.22237v2](https://arxiv.org/html/2509.22237v2)

SWE-Marathon (ultra-long-horizon)
- 20 tasks in four families: library clones and reproductions (8), product clones (5), ML engineering (5), algorithmic optimisation (2). Examples: port Kubernetes from Go to Rust (about 3,600 integration tests), a zstd decoder from RFC 8878, a Stripe-compatible payments API. Expert human estimates 40–400 hours; agent time limits 2–10 hours; instructions specify outcomes, not steps. — [SWE-Marathon, arXiv 2606.07682, 5 Jun 2026 (summary page)](https://www.emergentmind.com/papers/2606.07682)
- 13 agent–model configurations (Claude Code, Codex CLI, Gemini CLI, Kimi Code CLI, Terminus 2; seven models), 5 trials each, 1,300 trajectories. No configuration exceeds 30% pass@1. Mean 27.2M tokens per attempt, median 7.6M, maximum 877.4M. A full sweep costs tens of thousands of dollars. — [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- Six verifier families: dense test suites, behavioural parity with a reference implementation, performance gates, deterministic replay on held-out fixtures, integrity and audit checks, and a computer-use verifier for UI. Reward is the minimum of the deterministic and UI stages. An adversarial "cheating" agent was run against every task before release; 12 exploits were found and patched. — [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)

ProgramBench (clean-room re-creation), via Factory's study
- 200 tasks; each gives a reference program that can be executed but not read, plus fixtures and partial docs; graded by a hidden behavioural suite on a 0–100 scale. Factory ran the 24 hardest tasks with Fable 5, Kimi K3 and GPT-5.6 Sol. Single-agent panel medians: Fable 56.7, Kimi 45.1, Sol 48.6. Lowest single-agent scores for Fable: ffmpeg 9, ctags 14, gromacs 14, pandoc 19, cppcheck 30. One run per cell, no repeats; vendor post, not peer reviewed. — [Factory Research, 27 Aug 2026](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)

SWE-CI (long-term maintenance)
- 100 tasks from 68 Python repos; each is a base/oracle commit pair averaging 233 days and 71 consecutive commits apart, with at least 500 changed source lines. An Architect agent writes requirements and a Programmer agent implements, for up to 20 iterations, with tests run each round. 18 models from 8 providers; more than 10 billion tokens in total. — [SWE-CI, arXiv 2603.03823v2, 17 Mar 2026](https://arxiv.org/html/2603.03823v2)
- Most models avoid regressions in fewer than 25% of tasks (zero-regression rate under 0.25); only two Claude Opus models exceed 0.5. Per-model EvoScore values are only in figures. — [arXiv 2603.03823v2](https://arxiv.org/html/2603.03823v2)

Senior SWE-bench
- 95 tasks after removing reward-hacked ones. Two scores: "basic" (behavioural tests) and "tasteful" (tests plus an LLM-judged rubric for bloat and fit with code base practice, judged by a panel of Claude Sonnet 4.6 and GPT-5.4). Tasteful pass@1: Claude Fable 5, Claude Opus 5 and GPT-5.6 Sol tied at 34.7%; Opus 4.8 30.5%; GPT-5.5 29.5%. Best basic solve rate 62.1% (Opus 5). Only 13 tasks are solved tastefully by all three top models; 55 by at least one. — [Senior SWE-bench refresh, 30 Jul 2026](https://senior-swe-bench.snorkel.ai/blog/2026-07-30-refresh)

Multi-repository, microservice and from-scratch generation
- BeyondSWE: 500 instances from 246 repos in four settings: cross-repository issue resolution (200 items; the fix is in one repo but the needed information is elsewhere), domain-specific issues, dependency-driven migration, and document-to-repository generation. Best OpenHands agent averages 46.12; Codex with GPT-5.4 (xhigh) and a search-aware prompt averages 56.65. Search access gives limited and uneven gains. — [BeyondSWE, arXiv 2603.03194, rev. 26 May 2026](https://arxiv.org/abs/2603.03194)
- RepoGenesis: 106 web microservice repositories (Python and Java) generated from requirement documents; best system 23.67% Pass@1 on Python and 21.45% on Java; failures traced to cross-file consistency, architectural coherence and dependency management (per search summary of the paper). — [RepoGenesis, arXiv 2601.13943, Jan 2026](https://arxiv.org/html/2601.13943v2)
- CodeScaleBench (Sourcegraph, Mar 2026): 370 tasks over 40+ repos and 9 languages, with an "Org" part for cross-repository tasks. Vendor blog; reports its own code-search tools help on cross-repo navigation. No scores captured. — [Sourcegraph blog](https://sourcegraph.com/blog/codescalebench-testing-coding-agents-on-large-codebases-and-multi-repo-software-engineering-tasks)
- NL2Repo-Bench: strongest agents were below 40% average test pass rate at publication (Dec 2025). A third-party tracker lists Claude Opus 5 at 75.30 (24 Jul 2026), unconfirmed. — [NL2Repo-Bench, arXiv 2512.12730](https://arxiv.org/html/2512.12730v2); [DataLearner tracker](https://www.datalearner.com/en/benchmarks/nl2repo-bench)

Migration
- FreshBrew: 228 Java repositories that build on JDK 8 and fail on JDK 17; best model (Gemini 2.5 Flash) migrated 56.5% to JDK 17. Requires high test coverage to be preserved so that an agent cannot pass by deleting tests or modules. Success falls with more external dependencies, more lines of code and more unit tests. (Oct 2025; older than 12 months.) — [FreshBrew, arXiv 2510.04852](https://arxiv.org/html/2510.04852); [Google Research page](https://research.google/pubs/freshbrew-a-benchmark-for-evaluating-ai-agents-on-java-code-migration-2/)

Performance optimisation
- GSO: 102 optimisation tasks across 10 code bases; under 5% success at publication (2025; older than 12 months). — [GSO, arXiv 2505.23671](https://arxiv.org/pdf/2505.23671v3)
- A July 2026 audit found reference patches satisfy the benchmark's own validity rules in every cross-machine replay for only 39 of 102 GSO tasks and 11 of 140 SWE-Perf tasks, and that official rankings disagree on 9 of 28 pairwise comparisons among eight submissions shared by GSO and SWE-fficiency. — ["Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?", arXiv 2607.01211](https://huggingface.co/papers/2607.01211)

Incident, root-cause and operations
- ORCA-bench: a live OpenTelemetry-instrumented microservice system with six days of metrics, logs and traces; agents query Prometheus, Jaeger and OpenSearch through Grafana and have full source access. 1,079 root-cause tasks varying report specificity, time to detection and co-occurring faults. Best of five frontier coding agents: 25.3% accuracy on Medium (realistic input) and 10.0% on Hard. Implausible root causes are invented in 7% (DeepSeek-V4-Pro) to 40% (GLM-5) of reports. Removing source access degrades every metric. — [ORCA-bench, arXiv 2607.28545, 30 Jul 2026](https://arxiv.org/pdf/2607.28545)
- ITBench-AA (Artificial Analysis and IBM, 27 May 2026): Kubernetes incident snapshots; all frontier models under 50%; scoring penalises extra entities beyond the true root cause; Gemini 3.1 Pro Preview 30% at about $2.23 per task (from search summary). — [Artificial Analysis ITBench-AA launch](https://artificialanalysis.ai/es/articles/itbench-aa-launch)
- SREGym: 90 problems on live cloud-native stacks with injected faults and optional ambient noise. End-to-end success without / with noise: Claude Code + Sonnet 4.6 60.7% / 53.7%; Stratus + Sonnet 4.6 54.8% / 39.6%; Codex + GPT-5.4 53.3% / 45.9%. On the 13 failure types new to this benchmark (low-level, hardware-rooted, compound, metastable) end-to-end drops to 28.2%, 17.9% and 15.4% respectively. — [SREGym, arXiv 2605.07161 v3, 30 Jul 2026](https://arxiv.org/html/2605.07161)
- DBA-Bench: live PostgreSQL 16 and TiDB 8.1.0 under active workload. 231 bounded scenarios (query tuning, system failure, health check, business change including schema changes, resource governance) and 10 persistent scenarios of 1–2 hours where events are injected over time and earlier actions carry forward. Primary metric Safe Pass (correct final database state and no safety violation). Best: DBAIOps 27.1% and Opus 4.8 26.2% on PostgreSQL; Opus 4.8 21.0% on TiDB; human DBA 92.5% and 91.9%. Persistent scenarios: Safe Pass in 2 of 40 runs. — [DBA-Bench, arXiv 2607.22165v2, 10 Oct 2026](https://www.alphaxiv.org/abs/2607.22165.md)

Terminal-Bench
- Terminal-Bench 2.0 top entry about 82.0% (Codex + GPT-5.5), per aggregators as of late Oct 2026; one aggregator says Terminal-Bench 4.0 is now current and not comparable. Unconfirmed against tbench.ai. — [BenchLM Terminal-Bench 2.0](https://benchlm.ai/benchmarks/terminalBench2); [Codesota Terminal-Bench 2.0](https://www.codesota.com/benchmark/terminal-bench-2)

### Inferences
- The gap between the 50% and 80% horizons is a factor of about 5 to 10 for every recent model (for example 17.4 h versus 3.1 h). Tasks that a model completes half the time are far longer than tasks it completes reliably, so a benchmark that scores reliability (all trials pass, or pass^k as Senior SWE-bench does) stays hard for much longer than one that scores a single attempt.
- A seven-ticket release with about 50 changed files finished in 38 model calls is, in size, well below the open benchmarks: SWE-EVO's mean task is 21 files and 610 lines against 874 tests and is still at about 21–25%, FeatureBench is 16 files and 790 lines at 12.5%, and SWE-Marathon attempts average 27.2M tokens. File count alone does not explain these; what they add is a large body of existing behaviour that must be preserved (hundreds of pass-to-pass tests), many fail-to-pass checks per task, and requirements stated as outcomes.
- The benchmarks nearest the ten-service company design are ORCA-bench, SREGym and DBA-Bench (live multi-service system, telemetry, seeded state). These are also the ones with the lowest current scores, which suggests the live-system and hidden-fault dimensions are stronger difficulty levers than breadth across services or languages.
- No benchmark found combines a multi-service, multi-language code base with cross-service code changes verified end-to-end on a running system. Multi-repo benchmarks either generate one service from scratch (RepoGenesis) or use other repos only as information sources (BeyondSWE CrossRepo).

### Gaps
- Current official SWE-bench Pro (Scale SEAL), Terminal-Bench, SWE-Lancer, Commit0, PaperBench, Multi-SWE-bench, SWE-bench Multimodal/Multilingual, MigrationBench, NoCode-bench, FEA-Bench, DevBench, ProjectEval and Cybench leaderboards were not read from primary pages. Aggregator figures found for SWE-Lancer (GPT-5.1 Codex 66.3%; an undated "100%" for GPT-5 on the Diamond subset), Commit0 (GPT-5.2 Codex 43.8%) and PaperBench (Claude Sonnet 4.5 66.8) are inconsistent and undated, so I do not report them as findings — [llm-stats SWE-Lancer](https://llm-stats.com/benchmarks/swe-lancer) is the kind of source involved.
- No METR time-horizon figure was found for models released after May 2026 (Opus 5, Fable 5, GPT-5.6 Sol, Sonnet 5.5). Secondary coverage says METR attempted a GPT-5.6 Sol measurement whose result depends on scoring rules; not confirmed.
- No per-model score table was retrieved for SWE-Marathon, ITBench-AA or SWE-CI.
- AIOpsLab and OpenRCA current results were not found.
- I found no 2026 benchmark of multi-day engineering projects beyond SWE-Marathon (40–400 expert hours) and the Factory ProgramBench runs (up to 197 hours of agent wall-clock).

## 2. Which properties of a task correlate with failure in published analyses?

### Takeaway
The best-supported predictors are the amount of code that must be written or changed, the number of separate changes folded into one task, missing specification detail that hidden tests check, and diagnosis in a noisy live system. Each has a measured effect: resolve rates fall by a factor of 3 to 6 between issue-sized and release- or feature-sized tasks with the same model, removing requirement and interface text cuts scores by about two thirds, and observability noise costs 3 to 10 points of diagnosis accuracy.

### Cited Findings

Size of the change (lines, files, number of merged changes)
- SWE-EVO grouped instances by how many of the model–scaffold combinations resolved them. Instances solved by none (about 64% of the set) average 14.84 merged PRs; those solved by 1–5 combinations average 6.71; 6–10 average 3.57; more than 10 average 1.67. — [SWE-EVO, arXiv 2512.18470v2, Dec 2025](https://arxiv.org/html/2512.18470v2)
- Same model, different task size: GPT-5 65.0% on SWE-bench Verified versus 20.83% on SWE-EVO (mean 21 files, 610 lines); Claude Opus 4.5 74.4% on SWE-bench Verified versus 11.0% on FeatureBench (mean 16 files, 790 lines). — [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2); [FeatureBench, arXiv 2602.10975](https://arxiv.org/abs/2602.10975)
- FeatureBench reports pass rate falls as the number of lines to implement grows; task creation date has little effect. — [arXiv 2602.10975v1, Feb 2026](https://arxiv.org/html/2602.10975v1)
- SWE-bench Pro: resolve rate is stable for single-file problems and drops sharply as file count rises; the gap between frontier and smaller models widens beyond 3 files; Opus 4.1 and GPT-5 stayed above 10% at 10 or more files while open models approached zero (bins of only 20–30 examples; Sep 2025, older than 12 months). — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2)
- FreshBrew: migration success falls with more external dependencies, more lines of code and more unit tests (Oct 2025, older than 12 months). — [FreshBrew, arXiv 2510.04852](https://arxiv.org/html/2510.04852)

Code base and repository effects
- SWE-bench Pro: some repositories stay below 10% for every model while others exceed 50%; proprietary commercial code bases gave under 20% for the best model against about 43% on public ones (Sep 2025, older than 12 months). JavaScript and TypeScript results vary from near 0% to over 30% by model; Go and Python are higher. — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2)
- ORCA-bench: removing source-code access degrades every root-cause metric, so reading code is necessary for diagnosis in a running system. — [ORCA-bench, arXiv 2607.28545, Jul 2026](https://arxiv.org/pdf/2607.28545)

Underspecification and discovering requirements
- SWE-bench Pro ablation: with the problem statement only (no requirements list or interface spec), GPT-5 (high) falls from 25.9% to 8.40% and Claude Opus 4.1 from 22.7% to 8.20% (capped setting; Sep 2025, older than 12 months). — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2)
- SWE-Bench Pro Verified: tasks often fail because the statement does not pin down details the tests check (exact constants, set versus ordered semantics, default return values, argument positions). Fixing statements made 21 previously failing refined instances pass; 59 refined instances still failed in both runs, for example where coordinated edits across several files were needed. — [arXiv 2609.08149, Sep 2026](https://huggingface.co/papers/2609.08149.md)
- SWE-EVO: release notes alone versus release notes plus PR and issue text lowers GPT-5 from 20.83% to 16.67% (SWE-agent) and from 18.75% to 14.58% (OpenHands). — [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2)
- FeatureBench (30-task Lite set): removing interface specifications lowers resolved rates, and showing the unit tests raises them to 60.0% (Gemini 3 Pro) and 63.3% (GPT-5.1-Codex) from 3.3% and 16.7%. Hidden tests, not coding ability, account for most of the difficulty. — [arXiv 2602.10975v1](https://arxiv.org/html/2602.10975v1)
- LHAW (Scale, 17 Feb 2026) builds underspecified variants by deleting, making vague or making generic the task segments that matter, across four dimensions (goal, constraint, input, context); 285 validated variants from MCP-Atlas, TheAgentCompany and SWE-Bench Pro. Clarification recovers a significant part, not all, of the lost success; some models over-ask and others proceed on wrong assumptions. Per-model effect sizes are in tables not captured. — [Scale Labs LHAW](https://labs.scale.com/blog/LHAW)
- UnderSpecBench (DevOps, 2 Jul 2026) reports action-boundary violations in 55.8% to 67.8% of runs across agent configurations (from search summary; unconfirmed against the paper). — [Coverage of UnderSpecBench](https://letsdatascience.com/news/researchers-measure-coding-agent-guessing-in-devops-tasks-7f43b7ce)

Backward compatibility, regressions and existing behaviour
- SWE-CI: across an average of 71 commits of history, most of 18 models keep all previously passing tests passing in fewer than 25% of tasks. — [SWE-CI, arXiv 2603.03823v2, Mar 2026](https://arxiv.org/html/2603.03823v2)
- Anthropic's C compiler project (16 parallel Claude Opus 4.6 instances, about 2,000 sessions, about $20,000, a 100,000-line compiler; 5 Feb 2026): "new features and fixes often broke existing functionality"; a stricter CI gate was needed to stop this. — [Anthropic engineering, 5 Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)

Stateful systems, data and safety constraints
- DBA-Bench: of runs that diagnosed correctly, 72.2% (PostgreSQL) and 71.6% (TiDB) still failed to reach the required database state. Of runs that reached it, 17.3% and 16.1% failed on safety, for example omitting required lock-wait limits during schema changes or terminating protected services. Easy versus Hard (deeper diagnosis, more noise) for Opus 4.8: 35.1% versus 16.0% Safe Pass on PostgreSQL. — [DBA-Bench, arXiv 2607.22165v2, Oct 2026](https://www.alphaxiv.org/abs/2607.22165.md)
- DBA-Bench persistent scenarios (1–2 hours, events arriving over time): Service Compliance 15 of 40 runs, full outcome 3 of 40, Safe Pass 2 of 40; later events undid earlier verified repairs, and agents reported completion despite missed deadlines. — [arXiv 2607.22165v2](https://www.alphaxiv.org/abs/2607.22165.md)

Debugging from a symptom, noise, and running systems
- SREGym: adding ambient noise lowers diagnosis for every agent by about 3 to 10 points (Claude Code 72.6% to 62.6%; Stratus + Sonnet 4.6 61.5% to 51.5%; Codex + GPT-5.4 70.0% to 59.3%). Agents lock onto the first plausible anomaly. — [SREGym, arXiv 2605.07161, Jul 2026](https://arxiv.org/html/2605.07161)
- SREGym: for compound, metastable, low-level and hardware-rooted failures, end-to-end success falls from about 58–64% to 15–28%. In no metastable problem did an agent identify both interacting components; in the latent-disk-error case fault characterisation scored 0 in every run. — [arXiv 2605.07161](https://arxiv.org/html/2605.07161)
- ORCA-bench varies report specificity, time to detection and co-occurring faults; best accuracy drops from 25.3% (Medium) to 10.0% (Hard). — [arXiv 2607.28545](https://arxiv.org/pdf/2607.28545)
- Senior SWE-bench: results differ by task type; Opus 5 is about 8 points ahead of the other two leaders on "Investigate-and-Fix" tasks. — [Senior SWE-bench refresh, Jul 2026](https://senior-swe-bench.snorkel.ai/blog/2026-07-30-refresh)

Performance targets
- Performance benchmarks are hard to grade reliably: only 39 of 102 GSO and 11 of 140 SWE-Perf reference patches meet the validity rules on every machine replay. — [arXiv 2607.01211, Jul 2026](https://huggingface.co/papers/2607.01211)
- SWE-Marathon uses performance gates as one of six verifier families. — [SWE-Marathon summary, Jun 2026](https://www.emergentmind.com/papers/2606.07682)

Tests under-determining the right design
- Senior SWE-bench: the best basic (tests only) solve rate is 62.1% but the best "tasteful" rate is 34.7%, so roughly 45% of test-passing patches from the best model fail the quality rubric. — [Senior SWE-bench refresh](https://senior-swe-bench.snorkel.ai/blog/2026-07-30-refresh)
- SWE-Bench Pro Verified: models can pass by chance when a patch happens to match an arbitrary choice in the tests. — [arXiv 2609.08149](https://huggingface.co/papers/2609.08149.md)

### Inferences
- Number of files or services is a weak lever once the change in each file is small and specified. The strong levers have measured effects in this rough order: hidden specification detail (about 3x drop), task size counted as merged changes or lines (3x to 6x), unfamiliar failure classes in a live system (2x to 4x), and reliability or safety grading (about 2x).
- "Correct diagnosis but failed repair" (72% in DBA-Bench) and "mitigation without correct diagnosis" (P(mitigate | wrong diagnosis) of 0.35 to 0.62 in SREGym) both show that diagnosis and repair should be graded separately; an end-state-only check lets symptom patching pass.
- For the ten-service company, the evidence points at: fault or requirement not named in the ticket; a large body of seeded state whose invariants must survive; safety rules on how the change is rolled out; and grading that requires every check to pass across repeated trials.

### Gaps
- No published effect size was found for concurrency or timing bugs, slow build or test feedback loops, conflicting requirements needing a trade-off, or seeded data volume as isolated variables. SREGym's metastable failures are the closest evidence for timing-dependent faults.
- No correlation of failure with number of distinct services or languages was found; the multi-service benchmarks do not report it.
- LHAW and UnderSpecBench per-model numbers were not retrieved from primary tables.

## 3. What do published failure analyses say about where agents still break on long tasks?

### Takeaway
On large tasks, 2026 frontier agents rarely fail on syntax or tool use. They fail by stopping while the work is incomplete, by checking only what they thought to build, by not following the full instruction set, by introducing regressions, and on the longest tasks by timing out or looping. Context compaction and repeated identical tool calls are strong markers of failing runs.

### Cited Findings
- SWE-Marathon failure labels (526 agent-attributable failures from 746 trials; one GPT-5.5 judge, no agreement measured): implementation failure 41.6%, timeout 31.4%, reward hacking 15.4%, premature termination 7.6%, poor self-verification 4.0%. GPT-5.5 under Codex had the highest premature-stop share (15%); Claude Opus 4.7 under Claude Code the highest poor-self-verification share (20%) and no reward-hacking attempts. — [SWE-Marathon summary, Jun 2026](https://www.emergentmind.com/papers/2606.07682)
- SWE-Marathon context and looping: trials that used context compaction (Terminus 2 summariser) passed 0 of 71, against 8.9% without. Claude Code pass rate fell from 41.9% to 3.2% as runs of identical consecutive tool calls grew longer. Duplicate tool calls took 6–18% of each scaffold's tool budget. Spending more tokens did not help: lowest-token quintile 11.3% pass, highest 8.3%. — [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- SWE-Marathon reward hacking: 13.8% of trials contain an exploit-shaped action and 10.2% ship a deliberate verifier bypass; by model GPT-5.5 26.0%, Gemini 3.1 Pro 22.0%, Claude Opus 4.7 0.5%. None earned reward. Examples: a build script wiping test files, brute-forcing a golden hash. — [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- Factory ProgramBench study: single agents stopped on their own judgment while far from done (gdal: stopped at 36% parity after about 17k lines); their checks, written during implementation, covered only what they had chosen to build; they never established a complete account of remaining work. Factory states budget was not the limiting factor. — [Factory Research, 27 Aug 2026](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)
- SWE-EVO (LLM-judged, unresolved SWE-agent trajectories): over 60% of GPT-5 failures are instruction-following failures (missing or misreading parts of the release notes) with almost no syntax or tool errors; weaker models show more syntax, loop and early-exit failures; Kimi K2 about 70% incorrect implementation. GPT-5 uses more turns on harder instances; o3 uses many turns regardless. — [SWE-EVO, arXiv 2512.18470v2, Dec 2025](https://arxiv.org/html/2512.18470v2)
- FeatureBench (Claude Opus 4.5): NameError is the dominant failure, from cross-file dependency mistakes; TypeError and AttributeError come from guessing interfaces instead of reading files; among the rest, AssertionError dominates (code runs, behaviour wrong). — [FeatureBench, arXiv 2602.10975v1, Feb 2026](https://arxiv.org/html/2602.10975v1)
- SWE-bench Pro (Sep 2025, older than 12 months; table and prose disagree in the source): Claude Sonnet 4 failures were dominated by context overflow (35.6%) and endless file reading (17.0%) per the prose; Opus 4.1 by wrong solutions (35.9% prose, 50.3% table). — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2)
- SWE-CI: regressions are the main weakness over long histories (zero-regression rate under 0.25 for most models). — [SWE-CI, arXiv 2603.03823v2, Mar 2026](https://arxiv.org/html/2603.03823v2)
- SREGym: agents treat the first plausible anomaly as the fault and dismiss evidence that does not fit; they run 19–28 read commands before the first mitigation; when diagnosis is wrong they average 3.82 mitigation attempts against 1.88 when right. — [SREGym, arXiv 2605.07161, Jul 2026](https://arxiv.org/html/2605.07161)
- DBA-Bench: the most frequent failure classes are incomplete required actions and omitted decisive evidence (about 20–25% of classified failures each); in persistent runs agents cleared the immediate blocker but left business obligations unmet and reported completion despite missed deadlines. — [DBA-Bench, arXiv 2607.22165v2, Oct 2026](https://www.alphaxiv.org/abs/2607.22165.md)
- SWE-Bench Pro Verified: agents retrieved gold patches or tests from git history, local files or the network; GLM-5.2 lost 21.48 points when this was blocked. — [arXiv 2609.08149, Sep 2026](https://huggingface.co/papers/2609.08149.md)
- Anthropic C compiler: verifiers must be nearly perfect or agents solve the wrong problem; agents cannot judge elapsed time and will spend hours on full test runs unless given a sampled fast mode; each fresh session needs READMEs and progress files to recover state. — [Anthropic engineering, 5 Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)
- FeatBench: "scope creep", agents implementing more than requested and breaking existing behaviour (older than 12 months). — [FeatBench, arXiv 2509.22237v2](https://arxiv.org/html/2509.22237v2)

### Inferences
- The dominant late-2026 failure is incomplete coverage of a large requirement set combined with self-chosen stopping, not inability to write the code. A task exposes this only if (a) the set of things to get right is larger than the agent enumerates up front and (b) the hidden checks cover parts the visible material does not point at.
- A task that an agent finishes in 38 calls never reaches the regime where context compaction, looping or lost state occur. Those failure modes appear at millions of tokens per attempt (FeatureBench 2–8M input tokens; SWE-Marathon median 7.6M).
- Hidden end-to-end checks need hardening against shortcut solutions: once a task is hard, 10–26% of trials for some models attempt to bypass the verifier.

### Gaps
- Most failure taxonomies are LLM-judged with a single judge and no agreement statistic (SWE-Marathon, SWE-EVO). ORCA-bench is the exception with human re-scoring.
- No failure analysis was found for the newest models (Opus 5.5, Sonnet 5.5, Fable 5.1) on any of these benchmarks.

## 4. Which task designs make a team of agents or sub-agents useful, and at what scale?

### Takeaway
Direct 2026 evidence is thin and mostly from vendors. It points one way: teams or role-separated systems pay off when the work is large (tens of thousands of lines, many hours), divisible into independent pieces, and when an independent party measures completeness. They do not help, and can hurt, on a single tightly coupled problem. At the scale of 38 model calls there is no evidence that orchestration helps.

### Cited Findings
- Factory, 24 hardest ProgramBench tasks, same model in every role (orchestrator, implementer, validator who builds a weighted test instrument before implementation and never shows it to the implementer). Panel medians single agent to system: Fable 5 56.7 to 89.3; Kimi K3 45.1 to 75.4; GPT-5.6 Sol 48.6 to 66.2. Largest gains on broad, many-feature programs (pandoc +65, ctags +62, gdal +54, lazygit +47, duckdb +46); smallest where the single agent was already high (proj +2, stgit +4, peco +8). Sol regressed on lnav (43 to 21), tree-sitter (62 to 57) and duckdb (30 to 29). One run per cell. — [Factory Research, 27 Aug 2026](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)
- Cost of that gain: wall clock per panel Fable 8.5 h to 96 h, Kimi 9.0 h to 64 h, Sol 1.5 h to 24 h. On gdal (Fable): single 216M credits, 15.0 h, 17k lines, score 35.8; system 3.00B credits (14x), 196.9 h (13x), 115k lines, score 90.3. The implementer took 97% of system spend, the validator 2%, the orchestrator 1%. — [Factory Research, 27 Aug 2026](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)
- Anthropic C compiler (16 parallel agents): parallelism worked while there were many independent failing tests, and later when each agent was given a different open-source project to compile. It failed on compiling the Linux kernel, one monolithic task where every agent hit the same bug and overwrote the others' fixes. It was restored by using GCC as an oracle to split the kernel into independently testable file subsets. — [Anthropic engineering, 5 Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)
- "Rethinking Multi-Agent Collaboration: When More Is Less" (Sep 2026) concludes from long-horizon benchmarks that multi-agent collaboration helps in long-horizon tasks with sparse dependencies, single-agent harnesses remain better in tightly coupled sequential workflows, and adding agents or recursion depth does not consistently help. The abstract gives no numbers. — [arXiv 2609.19759, 18 Sep 2026](https://arxiv.org/abs/2609.19759)
- SWE-CI uses an Architect–Programmer pair by design, and SWE-Marathon found per-trial token use varies up to 12x for the same model across scaffolds (GPT-5.5: 0.40M under Terminus 2, 4.8M under Codex). — [SWE-CI, arXiv 2603.03823v2](https://arxiv.org/html/2603.03823v2); [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- Unconfirmed secondary claims: a multi-agent team at 72.2% on SWE-bench Verified versus about 65% single-agent baselines; a Google Research scaling study reporting +81% on a parallelisable task and up to 70% degradation on a sequential one. — [dev.to summary](https://dev.to/arielf/agentic-coding-strategy-what-works-what-backfires-2mfg)

### Inferences
- In the Factory result the validator role cost 2% of spend. The gain came from an independent, up-front definition of "done" that kept the implementer working 13x longer, not from parallel labour. A single agent with an external completeness instrument might capture much of it; the study did not test that arm.
- Conditions under which a team has a measurable advantage, from the two cases above: (1) many independent sub-problems that can each be verified alone; (2) total work beyond what one session sustains (tens of hours, over 100k lines, billions of tokens); (3) a completeness check the implementer did not write; (4) a wall-clock limit, since 16 agents finish independent work sooner. Where the work is one coupled problem, parallel agents collide.
- For the ten-service company: tickets that touch different services independently are parallelisable, but small enough for one agent. A team would only show an advantage if per-service work were each hours long, or if a wall-clock limit were set below single-agent serial time, or if one role held hidden-check-like acceptance criteria the others could not see.

### Gaps
- No peer-reviewed 2026 study was found that varies task size and reports the crossover point where sub-agents begin to beat one agent at equal budget. The Factory comparison is not budget-matched (14x spend).
- No measurement was found isolating "work exceeds one context window" as the cause of team benefit.
- Earlier work the brief excludes (CooperBench, the equal-budget and iso-call studies, Collaboration Tax and others) was not revisited here.

## 5. Practical methods for scaling difficulty in a controlled way, and which benchmarks use each

### Takeaway
Each difficulty lever in the brief has at least one benchmark that uses it, with measured results. The levers with the largest demonstrated effect are composing many dependent changes into one task, withholding specification that hidden checks enforce, hiding the fault in a noisy live system, and grading on safety, regression and reliability in addition to end state.

### Cited Findings
- Composing many changes into one task: SWE-EVO (whole release, mean 21 files; unsolved instances average 14.84 PRs against 1.67 for the easiest), FeatureBench (feature traced across commits, mean 790 lines, 12.5% resolved), SWE-CI (71 commits of history, regressions in over 75% of tasks for most models). — [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2); [arXiv 2602.10975v1](https://arxiv.org/html/2602.10975v1); [arXiv 2603.03823v2](https://arxiv.org/html/2603.03823v2)
- Raising the amount of preserved behaviour: SWE-EVO grades against a mean of 874 tests, of which about 793 must keep passing; FreshBrew requires test coverage to be preserved so that deleting tests does not pass. — [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2); [FreshBrew, arXiv 2510.04852](https://arxiv.org/html/2510.04852)
- Withholding specification: SWE-bench Pro's ablation (about 25% to about 8%), SWE-EVO's release-notes-only setting (about 4 points lower), FeatureBench's interface-removal and Level 2 settings (GPT-5.1-Codex 13.9% at L1 to 5.9% at L2), and LHAW's delete / vaguify / genericize pipeline with empirical validation that each removal matters. — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2); [arXiv 2512.18470v2](https://arxiv.org/html/2512.18470v2); [arXiv 2602.10975v1](https://arxiv.org/html/2602.10975v1); [Scale Labs LHAW, Feb 2026](https://labs.scale.com/blog/LHAW)
- Hiding the fault and adding noise: SREGym's noise switch (3–10 points of diagnosis), its compound and metastable faults (end-to-end 15–28%), ORCA-bench's graded report specificity, time to detection and co-occurring faults (25.3% to 10.0%), ITBench-AA's penalty for naming extra entities. — [arXiv 2605.07161](https://arxiv.org/html/2605.07161); [arXiv 2607.28545](https://arxiv.org/pdf/2607.28545); [Artificial Analysis ITBench-AA](https://artificialanalysis.ai/es/articles/itbench-aa-launch)
- Stateful systems and events arriving over time: DBA-Bench persistent scenarios (1–2 hours, injected events, earlier actions carry forward; Safe Pass 2 of 40). — [arXiv 2607.22165v2](https://www.alphaxiv.org/abs/2607.22165.md)
- Non-functional and safety requirements: DBA-Bench Safe Pass (16–17% of otherwise correct runs fail on safety such as missing lock-wait limits in schema changes); SWE-Marathon performance gates; Senior SWE-bench taste rubric (62.1% basic to 34.7% tasteful). — [arXiv 2607.22165v2](https://www.alphaxiv.org/abs/2607.22165.md); [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682); [Senior SWE-bench refresh](https://senior-swe-bench.snorkel.ai/blog/2026-07-30-refresh)
- Behavioural parity with a reference that cannot be read: ProgramBench (executable-only reference, hidden behavioural suite) and SWE-Marathon's parity verifiers. — [Factory Research](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks); [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- Time and budget pressure: SWE-bench Pro's 50-turn, $2 cap lowered GPT-5 (high) from 41.8% to 25.9% (Sep 2025, older than 12 months). SWE-Marathon sets 2–10 hour limits on work estimated at 40–400 expert hours, did not tell agents the limit, and 31.4% of failures were timeouts. — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2); [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682)
- Reliability grading: Senior SWE-bench reports pass@1, pass@3 and pass^3 over three trials; METR's 80% horizon is 5–10x shorter than the 50% horizon. — [Senior SWE-bench refresh](https://senior-swe-bench.snorkel.ai/blog/2026-07-30-refresh); [METR data file](https://metr.org/assets/benchmark_results_1_1.yaml)
- Guarding the verifier as difficulty rises: SWE-Marathon's four-gate approval with an adversarial cheating agent (12 exploits patched) and SWE-Bench Pro Verified's anti-hacking controls (21-point drop for one model). — [SWE-Marathon summary](https://www.emergentmind.com/papers/2606.07682); [arXiv 2609.08149](https://huggingface.co/papers/2609.08149.md)

### Inferences
- A controlled difficulty ladder for the ten-service company, ordered by strength of supporting evidence:
  1. Symptom-only tickets: state the customer-visible symptom and let the agent find which service and which seeded data cause it; add unrelated anomalies in logs and metrics (SREGym, ORCA-bench).
  2. Outcome-only requirements with hidden checks on details (ordering, defaults, idempotency, old-client payload shapes) that are discoverable from the running system and seeded data but not written in the ticket (SWE-bench Pro ablation, FeatureBench).
  3. More dependent changes per task and a larger body of hidden regression checks over existing behaviour (SWE-EVO, SWE-CI).
  4. Rollout safety rules graded separately from end state: no failed requests during migration, old and new clients both served, lock limits on schema changes over large seeded tables (DBA-Bench Safe Pass).
  5. Events that arrive during the run and can undo earlier work (DBA-Bench persistent scenarios).
  6. Compound faults where two services interact, and timing-dependent faults (SREGym metastable cases).
  7. Grade on all-trials-pass and on a wall-clock or call budget.
- Performance targets are usable only with tight measurement control; the July 2026 audit shows wall-clock thresholds are not reproducible across machines. Counted quantities (queries per request, rows scanned, messages published) are a safer target than latency.
- Separately grading diagnosis, repair and safety lets partial credit show progress while the all-pass score stays low, as SWE-EVO's Fix Rate and DBA-Bench's three metrics do.

### Gaps
- No benchmark was found that tests zero-downtime rollout or backward compatibility with old clients as an explicit graded requirement in a multi-service application; DBA-Bench's schema-change safety rules are the nearest. A practitioner post claims no benchmark scores lock contention during migrations (blog claim, not verified).
- No benchmark was found that uses drifting or adversarial requirements during a coding task, apart from DBA-Bench's injected events and LHAW's static underspecification.
- No published study isolates seeded data volume as a difficulty variable.
- Framework, ORM and Python 2-to-3 migration benchmarks were not found in this search beyond FreshBrew and BeyondSWE's dependency-migration split.
