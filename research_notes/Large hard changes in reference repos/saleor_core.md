## Key question 1: Which projects in saleor/saleor were the largest? (ranked list with tracking issue, PRs, size, areas touched)

### Takeaway
Three programmes stand clearly above the rest by size and duration: Promotions replacing Sales (one 32k-line feature-branch PR plus about 136 merged PRs with "promotion" in the title, 3.17 through 3.21), the Transactions API / payment apps replacing the Payments API (3.4 through 3.23, about 189 merged PRs with "transaction" in the title, a 17k-line landing PR that took seven months), and the tax rewrite (sync tax webhooks in 3.6 plus flat-rate tax API in 3.9, a 12.7k-line/241-file feature branch open for six months). Multichannel (3.0) is the largest single PR by commit count (553 commits, 283 files). Below those sit a set of medium-size but high-difficulty projects: checkout/order locking, deferred webhook payloads, voucher codes, int→UUID id migration, stock-availability decoupling, channel permissions.

### Inferences
- Ranking logic: rank 1–3 combine (a) the largest diffs (12k to 32k added lines, 120 to 318 files), (b) multi-release duration (each spans at least four minor releases and more than a year), (c) a live-data migration, (d) an old API kept working alongside the new one, and (e) a long tail of correctness fixes. Rank 4 (multichannel) has the largest single PR by commits but was shipped in a major version (3.0) where breaking everything at once was allowed, so its compatibility burden was lower.
- Rank 5 (concurrency) is small in lines per PR (#14885 is +30/-21; #19001 is +31/-7) but is the best evidence of "hidden invariants": the same class of bug is still being fixed five years after the first lock PR, and each fix is ported to three to six branches.
- For a benchmark that mirrors Saleor as ten services, the most transferable seeds are those whose difficulty is cross-cutting rather than volumetric: promotions (denormalised price + async recalculation + legacy API shim), transactions (two payment models coexisting, idempotent event reports, races with checkout completion), tax (external sync call inside price calculation with expiry and fallback), deferred webhook payloads (ordering/staleness semantics), and stock-availability decoupling behind a legacy flag.
- PR "size" for feature-branch PRs (#6242, #9784, #10350/#12401, #12980) understates PR count: each aggregated 10 or more reviewed sub-PRs that do not appear as merges to main.

## Key question 3: What specifically made each one hard (breakages, follow-up fixes, reverts, migration problems, compatibility shims, deprecation periods)

### Takeaway
Hardness came from five recurring sources, each with direct evidence: (1) two models running side by side for several releases (Sale + Promotion, Payment + Transaction, shipping-zone + channel stock, legacy + line-level discount propagation), usually behind a per-channel or shop-level legacy flag; (2) live-data migrations that had to run as batched, idempotent Celery tasks and themselves deadlocked; (3) price/tax/discount invariants that broke on each change; (4) concurrency between checkout completion, payment events and background recalculation; (5) every fix being ported to three to six release branches.

### Cited Findings

**Promotions**
- Dual-model rule: old sale mutations and queries are deprecated but keep working; when an old sale is modified through promotion-rule mutations "the sale will become the promotion rule and couldn't be handled by old sale migrations and queries anymore" — [RFC #12539](https://github.com/saleor/saleor/issues/12539).
- Migration: "Migrate all sales into new promotions"; each `Sale` becomes a `Promotion` flagged as an old sale and each `SaleChannelListing` becomes a `PromotionRule`; rollout via Celery task for zero downtime — [RFC #12539](https://github.com/saleor/saleor/issues/12539). Follow-up [#14711 "Move sale migration celery task"](https://github.com/saleor/saleor/pull/14711) and [#14537 "Fix migrations dependencies and revert options"](https://github.com/saleor/saleor/pull/14537).
- Behaviour reversal after release: 3.19 breaking change "Do not stack promotion rules within the promotion. Only the best promotion rule will be applied within the promotion. Previously discounts from all rules within the promotion that gives the best discount were applied to the variant's price" — [#15309](https://github.com/saleor/saleor/pull/15309), [3.19.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- Staged required field: `PromotionCreateInput.type` added optional in 3.19 ("will be required from 3.20"), required in 3.20 — [#14696](https://github.com/saleor/saleor/pull/14696), [#16296](https://github.com/saleor/saleor/pull/16296).
- Circular-call hazard: 3.19 breaking change "Disable the `order.discounts` field in sync events to prevent circular calls" — [#16111](https://github.com/saleor/saleor/pull/16111).
- Recalculation design churn: the dirty flag was moved between models ([#15338](https://github.com/saleor/saleor/pull/15338)); a bug in that path was still being fixed in November 2026 — "The `discounted_price_dirty` filter was built but never applied, so listings that were not marked dirty were recalculated too" — [#19984](https://github.com/saleor/saleor/pull/19984), [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md).
- Draft-order integration needed 178 commits and 60 review comments and also had to stop "multiple catalogue discounts applied to single line" — [#15459](https://github.com/saleor/saleor/pull/15459) (issues [#14586](https://github.com/saleor/saleor/issues/14586), [#15124](https://github.com/saleor/saleor/issues/15124)).
- User-visible bug report: "Checkout discount still applied on product/s when sale is deleted or the catalogue is empty" — [discussion #14617](https://github.com/saleor/saleor/discussions/14617). Revert: [#18458 Revert "Fix negative unit price on gift line in case promotion gift reward changes"](https://github.com/saleor/saleor/pull/18458) (2025-11).
- Rounding: RFC required a check for rounding errors with several units and a percentage discount — [RFC #12539](https://github.com/saleor/saleor/issues/12539); earlier 3.12 changed discount rounding from `ROUND_DOWN` to `ROUND_HALF_UP` ("an order for $13 … 12.5% discount … $11.38 … now … $11.37") — [#12041](https://github.com/saleor/saleor/pull/12041).

**Transactions API**
- The landing PR states: "The migration compatibility fails, but it will be handled in separate PR, the same with zero-downtime migrations"; open to-do items include "All renamed/deprecated fields should have a separate migrations for 3.11 (zero-downtime policy)" and "proceed migration test from 3.7 with existing transactionItem and transactionEvent. Make sure that all fields that become unique now are handled correctly" — [#12401](https://github.com/saleor/saleor/pull/12401).
- Preview-then-break cycle: 3.13 "Feature preview breaking change" — ownership rule ("any update action can be done only by the same app/user that performed `transactionCreate`", applied only to new items), `transactionRequestAction` now needs `HANDLE_PAYMENTS` not `MANAGE_ORDERS`, `TRANSACTION_ACTION_REQUEST` no longer fired from `orderVoid/orderCapture/orderRefund/…` — [3.13.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md). 3.15 then removed about 30 fields/enums deprecated in 3.13 (`voidedAmount`→`canceledAmount`, `reference`→`pspReference`, `TransactionStatus`, `TRANSACTION_ACTION_REQUEST` → three events) — [#13020](https://github.com/saleor/saleor/pull/13020).
- Settings relocation across three releases: `defaultTransactionFlowStrategy` deprecated on OrderSettings in 3.16, dropped in 3.18 — [#14671](https://github.com/saleor/saleor/pull/14671).
- Migration-task problems: [#12486 "Change the way of handling the update of transaction for celery migration tasks"](https://github.com/saleor/saleor/pull/12486), [#12503 "Fix deadlock in order events celery migrations task"](https://github.com/saleor/saleor/pull/12503) (both days after the 3.13 landing).
- Races between payment events and checkout completion fixed repeatedly in 2025 (see Rank 5 list) — e.g. [#17776](https://github.com/saleor/saleor/pull/17776) (+316/-72, base branch 3.20, i.e. fixed on a release two minors old and ported forward).
- Semantics changes late in life: 3.21 `transactionUpdate` metadata now merges instead of overwriting ([#17261](https://github.com/saleor/saleor/pull/17261)); `OrderGrantRefundCreateInput.transactionId` becomes required ([#17635](https://github.com/saleor/saleor/pull/17635)); `TransactionAction.amount` becomes non-null and sync-webhook `amount` becomes optional ([#17690](https://github.com/saleor/saleor/pull/17690)); new channels default to `TRANSACTION_FLOW` — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21). 3.22: zero-total orders no longer create a manual charge or emit `ORDER_MARKED_AS_PAID`; `CHECKOUT_FULLY_PAID` logic not triggered for zero-total checkouts — [3.22 changelog](https://github.com/saleor/saleor/blob/3.22/CHANGELOG.md). Revert: [#17682 Revert adding `createdAutomatically` to `TransactionEvent`](https://github.com/saleor/saleor/pull/17682).
- Automatic checkout completion (3.20) is off for existing instances and on for new ones because "Enabling it may break storefronts or connected services that query or update `Checkout` after a transaction is created"; "payment provider might sometimes return lower amount than the one you have requested"; `checkoutComplete` "is idempotent … only one `Order` will be created", but with `orderCreateFromCheckout(removeCheckout: false)` "multiple `Orders` may be created from a single `Checkout`" — [3.19→3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20).

**Tax rewrite**
- Design invariants from the RFC: "Prices are denormalized (indefinitely for orders, or for settings.CHECKOUT_PRICES_TTL for checkouts) until they are invalidated or expired"; multiple subscribed apps are iterated "until we get a proper response"; if no tax data, error at `CheckoutComplete`/`OrderCreateFromCheckout` — [#9526](https://github.com/saleor/saleor/pull/9526).
- Breaking changes in 3.9: Vatlayer dropped; `Product.chargeTaxes`, `Shop.chargeTaxesOnShipping`, `Shop.includeTaxesInPrices`, `Shop.displayGrossPrices` "no longer used" (config moved to `Channel.taxConfiguration`); five plugin-manager methods removed; CSV export column returns empty — [#9784](https://github.com/saleor/saleor/pull/9784), [3.9.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md). 3.6: return type of two plugin-manager methods changed — [3.6.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- Bug tail: "Order discount is applied 2 times when any tax app/plugin is active" [#10428](https://github.com/saleor/saleor/pull/10428)/[#10483](https://github.com/saleor/saleor/pull/10483) (3.6); "Fix inaccurate tax calculations" [#9799](https://github.com/saleor/saleor/pull/9799); "Fix checkout base prices when tax app is broken" [#15777](https://github.com/saleor/saleor/pull/15777)/[#15783](https://github.com/saleor/saleor/pull/15783); "Propagate voucher discount between checkout lines when charge_taxes is disabled" [#11632](https://github.com/saleor/saleor/pull/11632); "Fix undiscounted price taxation when prices are entered with taxes" [#16992](https://github.com/saleor/saleor/pull/16992); "Fix undiscounted price taxation … when the Avatax plugin is used" [#17253](https://github.com/saleor/saleor/pull/17253); revert of an extra quantize in `normalize_tax_rate_for_db` [#17777](https://github.com/saleor/saleor/pull/17777)/[#17782](https://github.com/saleor/saleor/pull/17782).
- External-call containment: 3.21 breaking — list queries (`checkouts`, `checkoutLines`, `me.checkouts`, `orders`, `draftOrders`, `me.orders`) "will no longer trigger external calls to calculate taxes" or shipping webhooks; single-object queries still recalculate — [#17268](https://github.com/saleor/saleor/pull/17268), [#17421](https://github.com/saleor/saleor/pull/17421), [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21). Country-resolution order change (shipping → billing → channel default) was breaking in 3.15 because it alters the tax country — [#13159](https://github.com/saleor/saleor/pull/13159).

**Concurrency**
- "Without it, we were seeing a lot of deadlocks, between checkoutComplete mutation and processing the webhook from payment provider" — [#14885](https://github.com/saleor/saleor/pull/14885) (+30/-21, 2 files, six ports).
- Lock-ordering rule discovered late: "`delete_checkouts` was missing the lock on checkout that causes the deadlock with search update; migration tasks was missing locks as well; `orderLineDelete` locks lines, `process_order_prices` locks first order then lines" — [#19001](https://github.com/saleor/saleor/pull/19001) (2026-03).
- Earlier the opposite fix: "Remove unnecessary database lock on discount during checkout complete mutation" — [#8174](https://github.com/saleor/saleor/pull/8174)/[#8182](https://github.com/saleor/saleor/pull/8182) (2021).

**Webhook pipeline / deferred payloads**
- Staleness semantics: "A deferred payload reflects the object's state when the background task runs"; rapid successive changes can yield duplicate newer values; fix is `payloadGeneration: IMMEDIATE` (3.23.41+) — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md), [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23).
- Read-replica lag: "in case of higher read replica lag we could unconsciously build the payload with old data"; fix waits with Celery backoff (1 s, 2 s, 4 s … 15 tries then mark deliveries failed) — [#18607](https://github.com/saleor/saleor/pull/18607); reverted two days later ([#18635](https://github.com/saleor/saleor/pull/18635)) and re-landed ([#18638](https://github.com/saleor/saleor/pull/18638)).
- "Turn off deferred for fulfillment events that are using dict to pass data" — [#19011](https://github.com/saleor/saleor/pull/19011). SQS: "Fixed Celery tasks losing their SQS `MessageGroupId` when retried" — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md).
- Sync webhooks no longer pre-fired before async order events (3.23) — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md); 3.18 "will no longer reattempt delivery for webhooks that return non-transient HTTP errors (400, 404, etc.) or redirects" — [#14566](https://github.com/saleor/saleor/pull/14566); 3.22 "Webhooks are no longer triggered for deactivated Apps" — [3.22 changelog](https://github.com/saleor/saleor/blob/3.22/CHANGELOG.md).
- Plugin-signature breakage: about 30 manager methods gained a `webhooks` parameter across 3.17 and 3.18 — [3.17.0/3.18.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md). Revert: [#13895 Revert "Enable subscription webhook dry runs …"](https://github.com/saleor/saleor/pull/13895); [#15659/#15660 revert of `prevent_sync_event_circular_query` on `checkout.deliveryMethod`](https://github.com/saleor/saleor/pull/15660).

**Stock**
- Legacy flag: `useLegacyShippingZoneStockAvailability` defaults true for existing instances, false for new; `address` argument on `Product.isAvailable`, `ProductVariant.quantityAvailable`, `ProductVariant.stocks` is ignored when disabled; four new per-channel stock webhooks must be registered, "each webhook supports only one filterable subscription field" — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23), [#19014](https://github.com/saleor/saleor/pull/19014).
- Migration bug: "Fix invalid allocation after migration" — [#5678](https://github.com/saleor/saleor/pull/5678). Reverts: [#16680/#16681 Revert "Fix fetching available collection points"](https://github.com/saleor/saleor/pull/16681).
- #7589 reservations took 73 review comments and three months; reservations must be updated with checkout lines, shipping zone, removed at completion, and counted in `availableQuantity` — [#7589](https://github.com/saleor/saleor/pull/7589).

**Voucher codes**
- Deprecated single-code fields return the first code: "the `code` will return first code, same `used` will returned `used` from the first `code`" — [discussion #14409](https://github.com/saleor/saleor/discussions/14409). Usage counter race fixed in four branches — [#15857](https://github.com/saleor/saleor/pull/15857). "Fix decreasing voucher code usage after changing `includeDraftOrderInVoucherUsage` to false" — [#17028](https://github.com/saleor/saleor/pull/17028).

**Line-level discount propagation (3.21)**
- Per-channel flag `useLegacyLineDiscountPropagation`: "Existing channels have it enabled by default. New channels have it disabled"; only affects orders created after the upgrade; percentage vouchers keep `PERCENTAGE` type instead of converting to `FIXED`; `unitDiscount.amount` no longer includes `ENTIRE_ORDER` voucher or order-promotion discounts — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21). Follow-up "Make sure to set default value for legacy-discount-propagation flag" — [#17658](https://github.com/saleor/saleor/pull/17658). Related bugs: "Fixed bug when manual line discount doesn't override line-level vouchers" [#16738](https://github.com/saleor/saleor/pull/16738); "Fix subtotal discount propagation" [#15980](https://github.com/saleor/saleor/pull/15980); "Fixes incorrect gift card balances after covering the full order total" [#17566](https://github.com/saleor/saleor/pull/17566).

**Zero-downtime migrations**
- Every upgrade guide from 3.17 on carries the same warning: migrate to the latest previous minor first and run the Celery worker so data migrations run asynchronously; "Otherwise, you will need to downtime your solution to ensure correct data migration" — [3.16→3.17](https://docs.saleor.io/upgrade-guides/core/3-16-to-3-17), [3.22→3.23](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23).
- Failures of the mechanism itself: deadlock in a migration task ([#12503](https://github.com/saleor/saleor/pull/12503), [#16974](https://github.com/saleor/saleor/pull/16974): "risk that celery task triggered by 0071 migration will cause a deadlock and miss data to process"); a task rewritten back to a standard migration ([#17461](https://github.com/saleor/saleor/pull/17461)); a migration re-applied because the Celery config was missing ([#18670](https://github.com/saleor/saleor/pull/18670)), which led to a CI check ([#18668](https://github.com/saleor/saleor/pull/18668)); "Fixed the `set_user_search_document_values` data migration task failing with a statement timeout on large user tables" and "Fixed migration `account.0103_create_default_customer_type` to respect `POPULATE_DEFAULTS`" — [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md); "Fix migration issue between 3.0 and main" [#9323](https://github.com/saleor/saleor/pull/9323); "Fix voucher migrations" [#9249](https://github.com/saleor/saleor/pull/9249); "Migration dependencies fix" [#9590](https://github.com/saleor/saleor/pull/9590).
- Multi-release column removal is visible in 3.24: "`ProductType.is_digital` was removed from the ORM model; the column itself will be dropped in 3.25"; preorder "database columns will be dropped in a later release" — [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md).

**Search**
- "Fix ORM crash when generating hundreds of search vector in SQL" and "stack depth limit exceeded crash when generating thousands of search vector in SQL" — [#10261](https://github.com/saleor/saleor/pull/10261), [#10279](https://github.com/saleor/saleor/pull/10279). Dirty-flag indexing "background task runs every minute to update search vectors for dirty checkouts, processing the oldest first" — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md); deadlock on that flag — [#18786](https://github.com/saleor/saleor/pull/18786). Pagination cursor format changed for attribute-sorted product lists (3.23) — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md).

**Explicit delivery options**
- Two refresh behaviours must coexist: new flow "keeps the assigned delivery unchanged and marks it as invalid when the refreshed data differs"; "The deprecated fields implicitly overwrite the details of the assigned delivery when a refresh returns different information. This is done to maintain backward compatibility" — [#18887](https://github.com/saleor/saleor/pull/18887). `checkoutComplete` with an Invalid problem returns an error; clients must check `__typename` before reading `problem.line` — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23).

### Inferences
- The "legacy flag on for existing tenants, off for new tenants" device appears at least five times (automatic checkout completion 3.20, line discount propagation 3.21, metadata webhook emission 3.22, shipping-zone stock 3.23, plus `TRANSACTION_FLOW` default for new channels). A benchmark task that requires adding such a flag, defaulting it by tenant age in a migration, and keeping both code paths correct is a faithful miniature of how Saleor ships hard changes.
- The revert-then-reland pairs (#18607/#18635/#18638; #18738/#18749; #16680) show that even small changes in these areas fail in production-like conditions that unit tests did not cover (replica lag, large tables).
- No public incident post-mortems were found; "incident" evidence is indirect (fix PRs opened against old release branches such as 3.14 and 3.20, with phrases like "we were seeing a lot of deadlocks").

### Gaps
- Review-comment text was not read for any PR (only counts and PR bodies), so "things reviewers caught" is evidenced only by review-comment counts (#7589: 73; #15459: 60; #9394: 57; #9526: 52).
- Upgrade guides for 3.12→3.13 and 3.8→3.9 returned HTTP 404 at both `/upgrade-guides/…` and `/upgrade-guides/core/…`; their content is unconfirmed (the 3.13 changelog links to `docs.saleor.io/docs/3.x/upgrade-guides/3-12-to-3-13`).
- Whether any promotions or transactions data migration caused customer-visible data loss is not documented in public sources found.

## Key question 4: Which required coordinated changes in other repositories and how was that sequenced

### Takeaway
Core lands first behind a preview label or a legacy flag; saleor-docs and saleor-dashboard PRs are linked from the core PR; dashboard exposes the new UI behind feature flags that are removed a release or two later; plugins are deprecated when a replacement app exists in saleor/apps and removed two to three minors later. Version-skew between core and dashboard is a documented hazard.

### Cited Findings
- Transactions: the core PR links the dashboard counterpart "PR for dashboard part: https://github.com/saleor/saleor-dashboard/pull/2233" and moves its migration guide into saleor-docs — [#12401](https://github.com/saleor/saleor/pull/12401).
- Promotions: core PR links docs [saleor-docs#874](https://github.com/saleor/saleor-docs/pull/874) — [#12980](https://github.com/saleor/saleor/pull/12980). Dashboard side: in dashboard 3.22.2 the feature flags were removed and "Discount rules: … The legacy discount UI has been removed"; "Improved refunds" and "Product and order filters … now use the new `where` API instead of `filter`"; "The legacy UI cannot be restored after upgrading" — [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22).
- Voucher codes: docs [saleor-docs#1000](https://github.com/saleor/saleor-docs/pull/1000) — [#14123](https://github.com/saleor/saleor/pull/14123). Stock decoupling: docs [saleor-docs#1771](https://github.com/saleor/saleor-docs/pull/1771) — [#19014](https://github.com/saleor/saleor/pull/19014).
- Core/dashboard version skew: "Early Dashboard v3.22.x releases are not compatible with later Core 3.22 versions"; Dashboard 3.23.x and Core 3.23.x are fully compatible; `mount`, `target`, `options` removed from `AppExtension` in favour of `mountName`, `targetName`, `settings`; extension validation moved from core to the dashboard — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23), [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md).
- Apps repo / plugin-to-app migration sequence: 3.9 drops Vatlayer; 3.21 drops the invoicing plugin and old Stripe plugin and deprecates `WebhookPlugin` hooks ("Move custom logic to a Saleor app that listens to webhooks"); 3.22 deprecates Braintree, Razorpay, Sendgrid, Dummy, DummyCreditCard, Avalara plugins with app replacements listed; 3.23 removes Adyen and NP Atobarai ("treat the migration to the official App as part of your 3.23 upgrade — not an optional follow-up"); 3.24 removes Authorize.Net, Razorpay, Braintree, Dummy, Sendgrid — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21), [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22), [3.23 blog](https://saleor.io/blog/3.23), [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md).
- App-side ordering constraint: "Cloud Customer Emails: It cannot be installed on 3.22 — stay on the SMTP app until you upgrade" — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23). App manifests: `requiredSaleorVersion` semver range ([#12164](https://github.com/saleor/saleor/pull/12164)) and `Saleor-Schema-Version` header in manifest fetch/install handshake ([#13075](https://github.com/saleor/saleor/pull/13075)) exist to coordinate app and core versions — [3.13/3.15 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- App-facing navigation break: apps relying on `/apps/` navigation through App Bridge must update to `/extensions` — [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22).
- Storefront-side obligations: 3.0 JWT refactor "Requires handling of JWT token in the storefront" ([#5734](https://github.com/saleor/saleor/pull/5734)); 3.20 automatic checkout completion (storefront must handle `checkout` returning `null`) — [3.19→3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20); 3.23 storefronts must adopt `deliveryOptionsCalculate` and handle HTTP 503 for media still being fetched — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23).
- Notification migration: `NOTIFY_USER` deprecated from 3.16; apps move to dedicated events with subscription queries, with a mapping table (e.g. `ORDER_CONFIRMATION` → `OrderCreated`); `domain`, `site_name`, `logo_url` are absent from the new payloads — [3.16→3.17 guide](https://docs.saleor.io/upgrade-guides/core/3-16-to-3-17).
- Tax apps: new `TaxableObjectDiscount.type` added "to inform tax apps how to distribute discounts" and core-side validation of tax-app responses — [#16630](https://github.com/saleor/saleor/pull/16630), [#16720](https://github.com/saleor/saleor/pull/16720). Payment apps: `paymentMethodDetails` and `idempotencyKey` are contract additions apps must adopt — [3.22 changelog](https://github.com/saleor/saleor/blob/3.22/CHANGELOG.md), [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md).

### Inferences
- The usual sequence is: (1) core adds the new API as `[Preview]` or behind a legacy flag; (2) docs PR merges with it; (3) dashboard ships UI behind a feature flag; (4) apps adopt the new webhook contract; (5) dashboard flag removed; (6) core deprecates then removes the old path. For a ten-service benchmark, steps 1, 4 and 6 map naturally onto "producer changes contract, consumers must tolerate both, then old path is removed" tasks.
- The core↔dashboard 3.22 incompatibility and the "cannot be installed on 3.22" app note suggest version-skew tolerance is a real, testable requirement.

### Gaps
- saleor-dashboard, saleor/apps, app-sdk and storefront repositories were not searched directly; PR numbers there (other than dashboard#2233 and the three docs PRs) are unconfirmed.
- No source was found that states how the multichannel (3.0) rollout was sequenced across dashboard and storefront.

## Key question 5: Which have behaviour an end-to-end test could verify from outside

### Takeaway
Almost all top-ranked projects are externally observable through GraphQL results, webhook payloads or post-migration data; only the attribute-relation refactor and parts of the dataloader/performance work are purely internal. The best black-box seeds are those with a stated numeric or state-machine rule in a changelog or upgrade guide.

### Cited Findings

Externally verifiable (API result, webhook payload, or stored data after migration):
- Promotions: best-rule-only within a promotion vs. previous stacking ([#15309](https://github.com/saleor/saleor/pull/15309)); old sales still readable through the Sale API after migration and converted when edited via promotion mutations ([RFC #12539](https://github.com/saleor/saleor/issues/12539)); variant `discounted_price` reflects promotion changes after the recalculation task; `PROMOTION_STARTED`/`PROMOTION_ENDED` events — [3.17.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- Rounding: 12.5% off $13 gives $11.37 with $1.63 discount (was $11.38/$1.62) — [#12041](https://github.com/saleor/saleor/pull/12041).
- Transactions: `checkoutComplete` idempotency ("only one `Order` will be created"), `CHECKOUT_NOT_FULLY_PAID` error, `checkout` returning `null` after automatic completion — [3.19→3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20); ownership rule for transaction updates and `HANDLE_PAYMENTS` requirement — [3.13.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md); `idempotencyKey` identical across delivery retries — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md); metadata merge semantics in `transactionUpdate` — [#17261](https://github.com/saleor/saleor/pull/17261); zero-total orders create no charge object and emit no `ORDER_MARKED_AS_PAID`; mixing old Payment with a Transaction on one checkout is rejected — [3.22 changelog](https://github.com/saleor/saleor/blob/3.22/CHANGELOG.md).
- Concurrency: concurrent `checkoutComplete` + `transactionEventReport`, concurrent voucher redemption (usage count), and `draftOrderComplete` returning `TAX_ERROR` on concurrent modification ("Retrying the mutation succeeds") are all observable by firing parallel requests — [#17776](https://github.com/saleor/saleor/pull/17776), [#15857](https://github.com/saleor/saleor/pull/15857), [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md).
- Tax: list queries make no external tax/shipping calls while single-object queries do — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21); country resolution order shipping → billing → channel default — [#13159](https://github.com/saleor/saleor/pull/13159); error at completion when no tax data is returned — [#9526](https://github.com/saleor/saleor/pull/9526); discount not applied twice with a tax app active — [#10428](https://github.com/saleor/saleor/pull/10428).
- Webhooks: no retry on 4xx/redirect ([#14566](https://github.com/saleor/saleor/pull/14566)); no delivery for deactivated apps ([3.22 changelog](https://github.com/saleor/saleor/blob/3.22/CHANGELOG.md)); `DEFERRED` vs `IMMEDIATE` payload content after two quick updates ([3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)); circuit-breaker state via `App.breakerState` and `appReenableSyncWebhooks` ([#16658](https://github.com/saleor/saleor/pull/16658)); `OrderUpdate`/`DraftOrderUpdate` emit no webhook when nothing changed ([#17507](https://github.com/saleor/saleor/pull/17507), [#17532](https://github.com/saleor/saleor/pull/17532)); metadata-only change emits only the metadata event unless legacy flag set ([3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)).
- Stock: availability by warehouse–channel link vs. shipping zone under the legacy flag; allocation "from any warehouse in the channel"; deallocation correct when several order lines share a variant — [#19014](https://github.com/saleor/saleor/pull/19014), [#17657](https://github.com/saleor/saleor/pull/17657); reservation expiry exposed as `stockReservationExpires` and counted in `availableQuantity` — [#7589](https://github.com/saleor/saleor/pull/7589).
- Voucher codes: deprecated `code`/`used` return the first code's values; usage is the sum of codes; single-use codes deactivate — [#14123](https://github.com/saleor/saleor/pull/14123), [discussion #14409](https://github.com/saleor/saleor/discussions/14409).
- Line discounts: `OrderLine.discounts`, percentage vouchers keep `PERCENTAGE`, flag default by channel age — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21).
- UUID ids: "the old ids still can be used for old orders" — [3.2.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- Search: prefix, boolean, phrase, accent-insensitive matching and `RANK` ordering; numeric attribute sort (`10` after `9`) — [3.23 changelog](https://github.com/saleor/saleor/blob/3.23/CHANGELOG.md).
- Delivery options: stale vs. invalid problems, completion blocked on invalid delivery — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23).
- Removals with data effect: "Existing webhook subscriptions to these events are deleted by a migration; a webhook left with no other events will stop being triggered"; upgrade removes `MANAGE_APPS` from all existing apps; bulk-delete limit of 100 ids returns `INVALID` — [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md), [3.23→3.24 guide](https://docs.saleor.io/upgrade-guides/core/3-23-to-3-24).
- Permissions: channel-restricted staff see only their channels' orders ([#10423](https://github.com/saleor/saleor/pull/10423)); attribute mutations require the permission matching the attribute type (3.24) — [main changelog](https://github.com/saleor/saleor/blob/main/CHANGELOG.md).
- Zero-downtime migration: observable as "old-version service keeps answering correctly while the new schema is applied and the backfill task runs in batches" — rules in [zero-downtime migrations doc](https://docs.saleor.io/developer/community/zero-downtime-migrations).

Mostly internal (weak external signal):
- Attribute–product/page relation simplification: no API change declared in the PR ("New migrations" only) — [#13407](https://github.com/saleor/saleor/pull/13407); externally only checkable as "attribute values unchanged after migration".
- Lazy legacy payload generation and `webhooks`-parameter plumbing: performance/query-count changes — [#13758](https://github.com/saleor/saleor/pull/13758), [3.17.0 changelog](https://github.com/saleor/saleor/blob/3.20.0/CHANGELOG.md).
- Checkout metadata moved to a separate model — [#11264](https://github.com/saleor/saleor/pull/11264).

### Inferences
- Highest-value benchmark seeds (large, hard, and black-box checkable), in order: (1) replace a discount model with a rule model while keeping the old API readable and migrating live rows in batches; (2) introduce a second payment model with idempotent event reports and guard races with order completion; (3) move price/tax calculation to an external synchronous call with cached results, expiry and containment of calls in list endpoints; (4) deferred webhook payload generation with an opt-out and replica-lag handling; (5) change stock-availability semantics behind a legacy flag defaulted by tenant age; (6) int→UUID id migration with old ids still accepted; (7) multi-code vouchers with compatibility fields and concurrent usage counting.
- Concurrency seeds need a harness that issues parallel requests; migration seeds need a harness that seeds data on the old version, upgrades, and compares API output while the backfill is still running.

### Gaps
- No Saleor-published end-to-end test suite was inspected to confirm which of these behaviours Saleor itself tests from outside.
- Performance-only projects (dataloaders, query-count reductions) were not ranked because they lack black-box correctness criteria.
