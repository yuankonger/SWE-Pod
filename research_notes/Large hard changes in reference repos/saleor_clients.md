## Q1. Which projects in saleor-dashboard were the largest?

### Takeaway
The biggest dashboard projects were all forced by core API changes and shipped behind dashboard feature flags over 1 to 2.5 years: Transactions API / split payments on the order page (7-month umbrella PR, then a second "improved refunds" rewrite in 2024), multichannel (2020-21, dozens of PRs touching every page), Promotions/discount rules (flag lived Nov 2023 to Sep 2025), conditional `where` filters (flag lived mid-2023 to Oct 2025), and the apps-to-extensions model. The most benchmark-relevant one is the newest: since Nov 2025 the dashboard is built against two core schemas at once (stable and `main`), with fields tagged as belonging to one schema only.

**D5. Multi-schema support: one dashboard codebase against two core generations (2025-06 onward)** — the most direct mirror of "old and new core at once"
- "POC of multi-schema approach" [#6070](https://github.com/saleor/saleor-dashboard/pull/6070) (opened 2025-11-14, merged 2025-11-18; 25 files, +91,027 −35,284, 26 commits [API; mostly generated]); body: lets the dashboard "work with both production (Saleor 3.22) and staging (Saleor main) API schemas simultaneously", tested with core branch `multi-schema-poc`.
- Design (from the repo's own doc): two schema files (`schema-main.graphql` for stable tags, `schema-staging.graphql` for core `main`), two full sets of generated hooks/types, selection by flag `FF_USE_STAGING_SCHEMA`, helpers `isStagingSchema()` / `isMainSchema()` / `getSchemaVersion()`, and a "skip-based" pattern where both the main and the staging query hook are declared and only one executes — [docs/multi-schema.md](https://github.com/saleor/saleor-dashboard/blob/main/docs/multi-schema.md)
- README: "The dashboard supports both Saleor generations at once, and which one a build speaks to is decided at build time, so each target is a separate Saleor and a separate bundle"; e2e runs `pnpm e2e` (stable 3.23), `pnpm e2e:main` (unreleased core main), `pnpm e2e:all` — [dashboard README](https://github.com/saleor/saleor-dashboard/blob/main/README.md)

## Q3. SDK and mobile example: how were API breaking changes handled for clients that cannot be redeployed at once? Any documented compatibility policy?

### Takeaway
There is no documented policy for clients that cannot be redeployed (mobile builds in the field), and no evidence that Saleor ever maintained one: the SDK was deprecated outright (May 2023) and the React Native example is a 4-commit, licence-less, archived stub. The only documented client/core compatibility statements are for the dashboard: use the "latest matching" dashboard minor for a core minor, with occasional per-feature minimum core patch versions, and since Nov 2025 a build-time two-schema mechanism.

### Cited Findings
- SDK deprecation announcement "The SDK is dead, long live the (auth) SDK", 2023-05-22, by patrys: "It's time to deprecate the old Saleor SDK… it tried to do too much and… GraphQL is more flexible for most operations"; it "will not see any work done other than security fixes"; replaced for auth only by `saleor/auth-sdk`. No statement about core-version compatibility and no end-of-life date; zero replies — [saleor discussion #12891](https://github.com/saleor/saleor/discussions/12891)
- `saleor/saleor-sdk`: MIT, archived, 106 merged PRs, last push 2024-06-10; rebuilt in mid-2021 for core 3.0 (auth API, generated types, auto token refresh: [#102](https://github.com/saleor/saleor-sdk/pull/102), [#110](https://github.com/saleor/saleor-sdk/pull/110), [#116](https://github.com/saleor/saleor-sdk/pull/116), [#126](https://github.com/saleor/saleor-sdk/pull/126), external auth [#144](https://github.com/saleor/saleor-sdk/pull/144)). README warns only that "Changes in the core user methods and tests may result in failing tests" — [saleor-sdk README](https://github.com/saleor/saleor-sdk)
- The legacy storefront tracked core 3.0 by pinning SDK pre-releases ("Use next SDK version (user channel token)" [saleor-storefront#951](https://github.com/saleor/saleor-storefront/pull/951); "Bump SDK" #991; "Update SDK version" #994).
- The dashboard itself carried a frozen vendored copy of `@saleor/sdk` with a second Apollo client and a second generated schema until 2026-08-31 — [dashboard#6889](https://github.com/saleor/saleor-dashboard/pull/6889)
- `saleor/auth-sdk`: created 2023-05-12, last push 2025-09-23; versioning concern documented in its README is Next.js 13/14 vs 15 cookie handling, not Saleor core versions — [auth-sdk README](https://github.com/saleor/auth-sdk)
- `saleor/example-react-native-typescript`: "Saleor Example: React Native App in TypeScript using Expo", 4 commits, no LICENSE file visible, no releases, archived 2024-10-09 (API: created 2021-07-08, last push 2024-10-04); nothing on API versioning — [repo](https://github.com/saleor/example-react-native-typescript)

Dashboard v3.23.x and Core v3.23.x are fully compatible."; self-hosters should use the latest matching dashboard — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)
- Per-feature minimum core versions appear in dashboard release notes: "Requires Saleor 3.23.42 or later" (#7034); "Saleor 3.23.30 and above… on older versions the update still succeeds" — [dashboard CHANGELOG](https://github.com/saleor/saleor-dashboard/blob/main/CHANGELOG.md); a web-search summary also quoted "Requires core >=3.20.68" for a service-name header change (primary source not opened: **unconfirmed**).
- Real field breakage from a version mismatch: dashboard v3.20.18 against core v3.17.62 failed on the channels page with `Cannot query field "automaticallyCompleteFullyPaidCheckouts" on type "CheckoutSettings"` (HTTP 400); fixed by upgrading core to 3.20.50; no maintainer reply — [saleor issue #17023](https://github.com/saleor/saleor/issues/17023) (2024-11-18). Older example of the same class: [saleor issue #5809](https://github.com/saleor/saleor/issues/5809) `Cannot query field "price" on type "ProductVariant"` (2020).
- Core-side mechanisms that protect un-upgraded clients: deprecate-then-remove across minors (fields "still works in 3.23, but… will be removed in a future release"; "will be removed in v3.24.0"), and per-channel/per-shop legacy-behaviour switches (`useLegacyLineDiscountPropagation`: existing channels on, new channels off; `useLegacyUpdateWebhookEmission`; `useLegacyShippingZoneStockAvailability`: "Existing instances have this set to `true` to preserve backwards compatibility") — [3.20→3.21](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21), [3.22→3.23](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)
- Behavioural (non-schema) breaking changes that would hit an old client silently: `accountRegister` "no longer returns an error when the user already exists" (returns a user with empty `id`); logged-in `checkoutCreate` now honours the `email` input; external shipping method id no longer in `checkout.privateMetadata` — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21)

### Inferences
- For the benchmark's "mobile app whose released builds cannot be changed", Saleor provides no direct precedent on the client side. The real precedents are on the core side (deprecation windows, legacy-behaviour flags defaulting on for existing tenants) and in the dashboard (schema-tagged fields, "on older versions the update still succeeds").
- A GraphQL client fails hard (whole query rejected with a validation error) when it selects one removed field. That failure mode, seen in saleor#17023 and dashboard#6871, is the natural "old build in the field" hazard to reproduce.
- Semantics-only breaks (same schema, different behaviour, such as `accountRegister`) are harder to detect than schema breaks and make better hard seeds.

### Gaps
- No written Saleor policy on how long deprecated fields are kept was fetched (the docs may have one under "API usage / deprecations"; not checked).
- No Saleor mobile SDK or maintained mobile example exists as far as these sources show; community React Native apps were not searched.
- auth-sdk licence and its release history against core versions were not verified.

## Q5. What made each hard: regressions, follow-up fixes, breakage on older cores, reverts

### Takeaway
Hardness came less from code volume than from (1) two data models alive at once per record, (2) the core contract moving during and after the client work, (3) multi-step saves that are not atomic, (4) permission-dependent queries, and (5) GraphQL's all-or-nothing validation when a client selects a field the server no longer has.

### Cited Findings
- Two models at once: old Payments UI had to be restored for orders with payments after the new UI was built (#3238), and UI must respect per-channel `markAsPaidStrategy` — [dashboard#2233](https://github.com/saleor/saleor-dashboard/pull/2233); core later had to forbid mixing the two APIs on one checkout because it "leads to inconsistent behavior" — [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22)
- Moving contract: "Missing fields after API changes" (#2769), "Dashboard OrderDetails updates after core changes" (#2933) during D1 — [dashboard#2233](https://github.com/saleor/saleor-dashboard/pull/2233); `OrderGrantRefundCreateInput.transactionId` became required in 3.21 — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21); `AppExtension` field renames in 3.23 — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)
- Feature dropped mid-project: external refunds notification (#2884) "feature removed" — [dashboard#2233](https://github.com/saleor/saleor-dashboard/pull/2233)
- Test fallout at merge: Cypress run before merging #2233 showed 5 failed, 2 flaky, 241 passed; TODO "Fix failing tests for some reason" — [dashboard#2233](https://github.com/saleor/saleor-dashboard/pull/2233)
- Wrong data sent to core: "Experimental filters: add tests and fix wrong data send to core" [#4039](https://github.com/saleor/saleor-dashboard/pull/4039); negated filters returning the same as positive ones — [issue #3272](https://github.com/saleor/saleor-dashboard/issues/3272); "Fix sending empty order condition in discount rules" [#4717](https://github.com/saleor/saleor-dashboard/pull/4717); "Fix showing empty product list due to sending empty attributes array" [#4137](https://github.com/saleor/saleor-dashboard/pull/4137)
- Non-atomic multi-step saves: a failed promotion save "no longer removes the end date" (two-step save); editing one channel of a multi-channel rule "removed every channel except the first and showed 'Rule updated'" — [dashboard CHANGELOG 3.23.44](https://github.com/saleor/saleor-dashboard/blob/main/CHANGELOG.md)
- Permission-dependent queries: vouchers demanded MANAGE_PRODUCTS because picker searches ran on page load and channel availability was requested unconditionally (#6893); OIDC login broke because the login mutation selected fields only authenticated requests may read (#6935); "Allow view taxes with product manage permission" [#2510](https://github.com/saleor/saleor-dashboard/pull/2510); "Allow user without app permission access apps view" [#4738](https://github.com/saleor/saleor-dashboard/pull/4738) — [dashboard CHANGELOG](https://github.com/saleor/saleor-dashboard/blob/main/CHANGELOG.md)
- Version mismatch breakage: every attribute page failed against 3.24 until [#6871](https://github.com/saleor/saleor-dashboard/pull/6871); channels page failed on dashboard 3.20.18 vs core 3.17.62 — [saleor#17023](https://github.com/saleor/saleor/issues/17023); "Early Dashboard v3.22.x releases are not compatible with later Core 3.22 versions" — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)
- Reverts (37 merged PRs with "revert" in title): "Revert 'Additional mounting points'" [#5647](https://github.com/saleor/saleor-dashboard/pull/5647), "Revert 'Refactor useUrlValueProvider'" [#6288](https://github.com/saleor/saleor-dashboard/pull/6288), "Revert 'Extract suspense in refund settings'" [#6159](https://github.com/saleor/saleor-dashboard/pull/6159), "Revert 'Change API_URI to API_URL'" [#4922](https://github.com/saleor/saleor-dashboard/pull/4922) (a config rename that broke deployments), "Revert the media upload limit pre-check" [#6767](https://github.com/saleor/saleor-dashboard/pull/6767), "Revert voucher details ref" [#5763](https://github.com/saleor/saleor-dashboard/pull/5763) — [search](https://github.com/saleor/saleor-dashboard/pulls?q=is%3Apr+is%3Amerged+revert+in%3Atitle)
- One-way upgrade: after 3.22 "you cannot revert to the legacy UI and functionality" — [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22)
- Storefront: checkout app token initialisation (#668), checkout finalize bugs (#765), "Fix Stripe charged bug" (#522), thumbnail rewrite hotfix (#768), "Allow only certain api urls" (#833), codegen broken by new core scalars (#1122, #1143) — [saleor/storefront PRs](https://github.com/saleor/storefront/pulls?q=is%3Apr+is%3Amerged)

### Inferences
- A release ticket that is "an order of magnitude harder" than ordinary features should combine at least two of: per-record dual model, a field removal that old clients still select, a behaviour-only change behind a per-tenant legacy switch, and a permission-scoped query.
- The reason for the #4922 revert (env var rename) is inferred from the title only.

### Gaps
- Root-cause write-ups (post-mortems) were not found for any of these; evidence is PR titles, changelog text and issue threads.
- I did not confirm which specific change made early dashboard 3.22.x incompatible with later core 3.22 (likely the `AppExtension` field renames, #6015: **unconfirmed**).

- The dashboard's own e2e design supports the "old and new core" check pattern: one suite, two targets ("`pnpm e2e` against the latest stable Saleor (3.23)", "`pnpm e2e:main` against Saleor's unreleased main branch"), each with its own bundle, database restored before every test — [dashboard README](https://github.com/saleor/saleor-dashboard/blob/main/README.md)

### Inferences
- Seed sketches that map onto a ten-service mirror with an immutable mobile build (all derived from the cited events, none copied):
  1. Core removes fields a released mobile build still selects (pattern of #6871 / saleor#17023): core must keep serving the old selection (or a gateway must), while web shop and dashboard move on; test by replaying the frozen build's exact queries against the new core.
  2. Payments → transactions with per-order dual model (D1): old orders keep old refund path, new orders need grant-then-send refund with a transaction id; mixing must be rejected; dashboard, shop, payment service, notifications all change.
  3. Sales → promotion rules with data migration and a per-channel legacy propagation switch defaulting on for existing channels and off for new ones (D3 plus 3.21 guide).
  4. `accountRegister`-style behaviour change (no error for existing user) and checkout email semantics change: schema identical, old mobile build misbehaves unless core keeps legacy behaviour per client/tenant.
  5. Checkout delivery contract (3.23): deprecated fields keep working for old builds while new clients must handle stale/invalid delivery problems.
  6. URL/route migrations with legacy redirects in shop and dashboard (`/apps`→`/extensions`, `/{channel}`→`/{locale}/{channel}`) while third-party apps and emailed links still use old paths.
  7. Permission-scoped queries: a page must not request data the current staff role cannot read (#6893, #6935), tested by loading pages as restricted users and asserting no permission errors.
- Each of the real projects above took a team months and tens of PRs; a benchmark task compresses that, so the difficulty must come from the constraint set (frozen client, dual data model, legacy defaults), not volume.

### Gaps
- No measurement exists of how hard these would be for an agent; ranking is my judgement from duration, PR counts, follow-up fix counts and cross-repo reach.
- Saleor blog posts and docs pages describing these features (for user-visible acceptance criteria) were not fetched.
