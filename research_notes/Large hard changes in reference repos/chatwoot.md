# Largest and hardest engineering projects in chatwoot/chatwoot (state as of 2026-11-13)

Method note (applies to every size figure below). Sizes were computed from a full clone of the `develop` branch of https://github.com/chatwoot/chatwoot taken on 2026-11-13 (HEAD `4194120d4`, 7,127 commits, first commit 2019-08-14, 212 files in `db/migrate`, 738 files under `enterprise/`). Chatwoot squash-merges, so one commit = one PR and the commit body is the PR description. "Lines" = additions + deletions from `git log --numstat`; "code lines" excludes locale files and swagger. Project totals were built by grouping PR titles with keyword patterns, so they are approximate (a few unrelated PRs may be included, and PRs with unrelated titles are missed). PR descriptions quoted or paraphrased below come from the squash-commit bodies and are linked to the PR. Release dates are from the GitHub releases API. Latest release: v4.19.1 (2026-10-24).

Licence: the root `LICENSE` is MIT with the carve-out "All content that resides under the `enterprise/` directory ... is licensed under the license defined in `enterprise/LICENSE`"; `enterprise/LICENSE` is "The Chatwoot Enterprise license", production use only under the Chatwoot Subscription Terms — [LICENSE](https://github.com/chatwoot/chatwoot/blob/develop/LICENSE), [enterprise/LICENSE](https://github.com/chatwoot/chatwoot/blob/develop/enterprise/LICENSE). No source code is copied in these notes.

## 1. Which projects were the largest? (ranked)

### Takeaway
By raw size the top three are Captain (AI assistant, ~110k code lines over 238 PRs, enterprise), the Vue 3/Vite migration plus the "next" UI (one 47k-line, 661-file PR plus ~100 follow-ups, MIT) and the Voice channel (~29k lines, 54 PRs, enterprise). For a multi-service benchmark the best seeds are smaller but harder boundary projects: WhatsApp BSUID identity migration, Shopify app-store install + billing + compliance webhooks, historical data imports (Intercom/Freshdesk), Assignment v2, the sidebar unread-count cache (caused a production incident and a revert), the reporting rollup table, and the webhook-signature hardening series (two reverts).

### Inferences
- Size and benchmark value diverge. Ranks 1–3 are large mainly in front-end and enterprise code; ranks 4–8, 13 and 14 are the ones whose difficulty came from data crossing a system boundary or from concurrency, which is what a ten-service benchmark can reproduce.
- A single agent solved a seven-ticket release in 38 calls; the Chatwoot projects that took the maintainers multiple stacked PRs, a revert and a re-land (unread counts, BSUID, Shopify billing, webhook signatures) are the right order of magnitude harder because the first plausible implementation was wrong in production.

### Gaps
- Totals are keyword-grouped from PR titles; I did not hand-audit every PR in each group.
- I did not find public tracking issues for most projects; Chatwoot tracks work in a private Linear workspace (PR bodies link `linear.app/chatwoot/issue/CW-…`, which are not publicly readable). Public GitHub issues exist only for some (listed below).
- Not covered from primary sources in this pass: message-table partitioning (no PR with "partition" in the title found on `develop`), a dedicated "notification system rewrite" (only incremental PRs found), audit logs beyond a PR list, custom roles, help center.

## 3. What made each hard (concrete evidence)

### Takeaway
The recurring causes of difficulty were: concurrency bugs found only under production load, identity/dedup problems when an outside provider changes identifiers, security checks that broke live traffic and were reverted, and derived-data caches whose rebuild cost was underestimated.

### Cited Findings
- Cache rebuild caused an outage: after v4.15.0 the filtered unread-count path ran a Redis `SCAN` over a per-user key pattern plus "4 fresh SQL passes per user" on every `/unread_counts/index` and `update_last_seen` request; "Threads blocked in the SCAN held their DB connections, the connection pool exhausted, Sidekiq jobs were discarded with `ActiveJob::DeserializationError` ... and the enqueued queue blew past 200K" — [#14769](https://github.com/chatwoot/chatwoot/pull/14769). Re-landed behind a flag ([#14885](https://github.com/chatwoot/chatwoot/pull/14885)) with rebuild throttling ([#14980](https://github.com/chatwoot/chatwoot/pull/14980)).
- Assignment race: under Assignment V2 "a single conversation could be reassigned dozens of times in a row", because each resolve/snooze enqueued an inbox-wide assignment job; fixed by atomically claiming the conversation — [#14495](https://github.com/chatwoot/chatwoot/pull/14495).
- Assignment capacity silently bypassed: a method defined directly on `Inbox` shadowed the enterprise module override, so V2 capacity checks were "unreachable (dead code)" on team-assignment paths — [#13904](https://github.com/chatwoot/chatwoot/pull/13904).
- Seat-limit race: "concurrent agent-create requests could all observe the same remaining seat"; fixed by locking the account row; API still returns `402 Account limit exceeded` — [#15029](https://github.com/chatwoot/chatwoot/pull/15029).
- Provider identity change with a deadline and a mid-flight reversal: issue title says support "needed before June 2026" ([#13837](https://github.com/chatwoot/chatwoot/issues/13837)); [#15175](https://github.com/chatwoot/chatwoot/pull/15175) states "The direction of this PR changed mid-flight" after discussion in #14931 and the production report in #15359; lifecycle events ignored meant "the next message under a rotated identifier can create a second contact and split the customer's history" — [#15357](https://github.com/chatwoot/chatwoot/pull/15357).
- Provider-side breakage after a well-meant change: sending `messaging_account_id` made WhatsApp Cloud sends fail from 9 Nov 2026 with "(#10) Viewer cannot access the provided Paid Message Account"; reverted — [#16602](https://github.com/chatwoot/chatwoot/pull/16602).
- Signature validation reverted twice: Twilio `X-Twilio-Signature` validation #13638 reverted by [#14125](https://github.com/chatwoot/chatwoot/pull/14125); Bandwidth callback authentication reverted by [#16577](https://github.com/chatwoot/chatwoot/pull/16577). Twilio media retry fix #15499 reverted by [#15502](https://github.com/chatwoot/chatwoot/pull/15502) "after redirect regression", redone as [#15504](https://github.com/chatwoot/chatwoot/pull/15504).
- Missing webhook authentication was a security advisory: [#14280](https://github.com/chatwoot/chatwoot/pull/14280) (GHSA-7rw7-pc8v-mrr3); SSRF through automation/macro webhook action — [#14155](https://github.com/chatwoot/chatwoot/pull/14155).
- Duplicate inbound events: Meta "can deliver the same webhook notification multiple times for a single message"; customers received duplicate `message_created` account webhooks — [#13523](https://github.com/chatwoot/chatwoot/pull/13523). Instagram first-message path uses a Redis mutex; events were dropped after mutex retry exhaustion — [#14647](https://github.com/chatwoot/chatwoot/pull/14647); earlier [#7701 "locking and retry in FB message parsing"](https://github.com/chatwoot/chatwoot/pull/7701), [#12154](https://github.com/chatwoot/chatwoot/pull/12154).
- Ordering between local commit and remote callback: WhatsApp webhook setup ran before the record was saved, so Meta's validation could arrive before the row existed — [#12176](https://github.com/chatwoot/chatwoot/pull/12176).
- Query-plan regression and revert: a batched conversation-list loader was reverted because "With prepared statements, Postgres can plan the loader's subqueries with a generic plan" that walks a conversation's whole history — [#16571](https://github.com/chatwoot/chatwoot/pull/16571). Earlier N+1 fix reverted [#7271](https://github.com/chatwoot/chatwoot/pull/7271).
- Large deletes time out: SLA policy deletion gave HTTP 500 `Rack::Timeout` on large histories — [#12944](https://github.com/chatwoot/chatwoot/pull/12944); account/inbox destroy needed batch pre-purge (`find_in_batches(5000)`) — [#12408](https://github.com/chatwoot/chatwoot/pull/12408).
- Growing table: "the [`reporting_events`] table grows linearly with event volume, and aggregation queries ... get progressively slower as accounts age"; fix is a daily rollup table written by upsert from the event listener plus a backfill service, gated on a new per-account `reporting_timezone` — [#13796](https://github.com/chatwoot/chatwoot/pull/13796). The read side first needed a behaviour-identical `DataSource` abstraction — [#13798](https://github.com/chatwoot/chatwoot/pull/13798).
- SLA semantics changed after launch: deadlines were "calculated using wall-clock time, ignoring business hours" — [#13392](https://github.com/chatwoot/chatwoot/pull/13392); resolved conversations' misses kept growing, fixed with a stable completion timestamp "shared through REST and realtime payloads" and special handling of legacy rows — [#15024](https://github.com/chatwoot/chatwoot/pull/15024).
- Feature-flag bit reuse and persisted meaning: #14885 reuses a deprecated flag slot and "resets the reused bit for existing accounts"; #15985 keeps deprecated flags in place "so persisted bits retain their meaning"; #13666 reclaims `mobile_v2` for `report_rollup` — [#14885](https://github.com/chatwoot/chatwoot/pull/14885), [#15985](https://github.com/chatwoot/chatwoot/pull/15985), [#13666](https://github.com/chatwoot/chatwoot/pull/13666).
- External platform review as a gate: Shopify's automated review failed on missing compliance webhooks and HMAC checks ([#13549](https://github.com/chatwoot/chatwoot/pull/13549)); billing was rejected by the App Store (Linear PLA-170 cited in [#13550](https://github.com/chatwoot/chatwoot/pull/13550)); the work had to be split so billing infrastructure merged "before the shared signup and authentication changes" ([#15756](https://github.com/chatwoot/chatwoot/pull/15756)).
- Outbound email abuse incident: per-account daily cap added after an "SES incident Jan 28" — [#13411](https://github.com/chatwoot/chatwoot/pull/13411); silent drops from SES suppression list: "The app still logs the send, so nobody sees a failure" — [#15989](https://github.com/chatwoot/chatwoot/pull/15989).
- Search indexing: reindex job storms and index "field explosion" — [#12618](https://github.com/chatwoot/chatwoot/pull/12618), [#12786](https://github.com/chatwoot/chatwoot/pull/12786); SQL fallback added a year later — [#16185](https://github.com/chatwoot/chatwoot/pull/16185).
- Revert count: 28 commits on `develop` have titles starting with "Revert"/"revert", 13 of them in 2026 (local `git log`, repository [commit history](https://github.com/chatwoot/chatwoot/commits/develop)).

### Inferences
- The hardest-to-get-right pattern in Chatwoot's history is "two external identifiers for one person" (phone vs BSUID, merged contacts, Brazil 9-digit duplicates, Instagram scoped ids). In a Saleor-like company the analogue is a customer whose commerce id/email changes or merges while orders and refunds keep arriving at the support desk.
- The second is "derived state kept in sync by events" (unread counters, reporting rollups, SLA deadlines): correct on a small dataset, wrong or too slow under concurrency. These can be made hard in a benchmark by testing with concurrent or replayed events rather than by adding code volume.

### Gaps
- Incident details (duration, customer impact) are only in PR descriptions; no public post-mortems were found in this pass. The Meta incident status page linked from #15210 was not retrieved.
- I did not read issue threads #13837/#14931/#15359 beyond titles and metadata.

## 4. Projects that exchange data with an outside system, and how failures, retries, ordering and duplicates were handled

### Takeaway
Chatwoot's commerce and payment integrations are pull-on-view (Shopify orders, Stripe invoices fetched when the sidebar opens) with webhooks used only for lifecycle (uninstall, GDPR). The richest failure-handling evidence is in the messaging channels and the import pipeline: dedup by source id, Redis mutexes, unique indexes with retry, signature checks, stall detection and guarded retry.

### Cited Findings
- Shopify orders: fetched from Shopify via OAuth token and rendered in the sidebar, no local order store at launch ("We might need to cache it in the future") — [#11101](https://github.com/chatwoot/chatwoot/pull/11101). Inbound: one HMAC-verified endpoint `POST /webhooks/shopify` for three compliance topics, 401 on mismatch — [#13549](https://github.com/chatwoot/chatwoot/pull/13549). Uninstall cleanup must not race with reconnect; OAuth state expires — [#16084](https://github.com/chatwoot/chatwoot/pull/16084). Per-workspace callback/webhook URLs keyed by account id for custom apps; credentials encrypted and never returned — [#15824](https://github.com/chatwoot/chatwoot/pull/15824).
- Stripe: read-only lookup by contact email, agent picks when several customers match; no webhook-driven updates — [#15765](https://github.com/chatwoot/chatwoot/pull/15765). Signed `account.application.deauthorized` removes the integration and tokens; in-flight refreshes are invalidated "so outdated responses and errors cannot overwrite the newer state" — [#16253](https://github.com/chatwoot/chatwoot/pull/16253).
- Intercom/Freshdesk import (polling a paginated API): durable source mappings, already-imported records logged as skipped, historical messages written "without normal outbound delivery callbacks", paginated skip/error logs — [#14922](https://github.com/chatwoot/chatwoot/pull/14922). Stall = no progress for 15 minutes; retry rotates the run id under an account lock and only if no other import is active — [#15050](https://github.com/chatwoot/chatwoot/pull/15050). Duplicate first message from ticket description fixed — [#15261](https://github.com/chatwoot/chatwoot/pull/15261).
- Outbound account webhooks: duplicates of `message_created` traced to duplicate provider deliveries — [#13523](https://github.com/chatwoot/chatwoot/pull/13523); per-webhook signing secret with backfill for existing rows — [#13573](https://github.com/chatwoot/chatwoot/pull/13573); event subscriptions per webhook — [#4540](https://github.com/chatwoot/chatwoot/pull/4540); missing `conversation.opened` on a legacy path — [#15509](https://github.com/chatwoot/chatwoot/pull/15509).
- Agent-bot webhooks: on 429/500 "delivery attempts complete first and then existing fallback handling runs" — [#13521](https://github.com/chatwoot/chatwoot/pull/13521). Max retries for all jobs — [#3582](https://github.com/chatwoot/chatwoot/pull/3582).
- Inbound channel webhooks: HMAC required for WhatsApp/Instagram (401 otherwise) — [#14280](https://github.com/chatwoot/chatwoot/pull/14280); Messenger rejects events with 400 when no app secret is configured — [#16576](https://github.com/chatwoot/chatwoot/pull/16576); Redis mutex + unique `(inbox_id, source_id)` index + retry for concurrent first messages — [#14647](https://github.com/chatwoot/chatwoot/pull/14647).
- Delivery status and retries: per-provider status callbacks ([#5157](https://github.com/chatwoot/chatwoot/pull/5157), [#8082](https://github.com/chatwoot/chatwoot/pull/8082), [#8136](https://github.com/chatwoot/chatwoot/pull/8136)); agent-initiated retry of failed messages limited to 24h — [#12436](https://github.com/chatwoot/chatwoot/pull/12436); read-status API for API channels documented — [#15469](https://github.com/chatwoot/chatwoot/pull/15469); campaign delivery analytics — [#15276](https://github.com/chatwoot/chatwoot/pull/15276).
- Email: IMAP polling job ([#8766](https://github.com/chatwoot/chatwoot/pull/8766)), OAuth token refresh ([#9603](https://github.com/chatwoot/chatwoot/pull/9603)), auth-failure to re-authorization prompt attempted and reverted twice ([#13671](https://github.com/chatwoot/chatwoot/pull/13671), [#15823](https://github.com/chatwoot/chatwoot/pull/15823)), null bytes in inbound mail ([#14546](https://github.com/chatwoot/chatwoot/pull/14546)), threading strategy refactor ([#12766](https://github.com/chatwoot/chatwoot/pull/12766)).
- Monitoring/alerts: scheduled WhatsApp phone-number health sync ([#15100](https://github.com/chatwoot/chatwoot/pull/15100)); Twilio webhook health tab ([#15011](https://github.com/chatwoot/chatwoot/pull/15011)); monitors post to Slack and fire automations only for live messages, "historical scans do not run actions", and automation-generated replies cannot re-trigger ([#16055](https://github.com/chatwoot/chatwoot/pull/16055), [#16161](https://github.com/chatwoot/chatwoot/pull/16161)).
- Voice: provider webhooks turned into `Call` records keyed by `call_sid` ([#14091](https://github.com/chatwoot/chatwoot/pull/14091), [#14315](https://github.com/chatwoot/chatwoot/pull/14315)).

### Inferences
- Mapping to the benchmark's boundaries: support desk ↔ commerce API = Shopify orders sidebar + compliance/uninstall webhooks (E), and the import pipeline (G) as "backfill a customer's history from commerce"; ↔ payments = Stripe sidebar and deauthorize webhook (F); ↔ email/notifications = email channel, outbound caps, suppression (L); ↔ monitoring = health sync, webhook health, monitors-to-Slack (K, M); outbound contract = account webhooks with secrets and dedup (N).

The benchmark's design (desk receives order and refund events) is therefore closer to Chatwoot's channel-webhook and import code paths than to its Shopify integration; the dedup/ordering lessons should be taken from D, G, M and N.

## 5. Which have outcomes an end-to-end test could check from outside

### Takeaway
Most boundary projects have externally observable contracts: HTTP status on signed/unsigned webhooks, exactly-once records after duplicate or concurrent deliveries, counts and timestamps in API responses, and absence of side effects (no emails or webhooks for imported history).

### Cited Findings
- Signed webhook endpoints: invalid HMAC returns 401, valid enqueues processing — [#13549](https://github.com/chatwoot/chatwoot/pull/13549), [#14280](https://github.com/chatwoot/chatwoot/pull/14280); unconfigured secret returns 400 — [#16576](https://github.com/chatwoot/chatwoot/pull/16576).
- Exactly-once assignment under concurrent jobs: "each unassigned conversation is assigned exactly once", observable as a single activity message — [#14495](https://github.com/chatwoot/chatwoot/pull/14495). Capacity respected on team paths — [#13904](https://github.com/chatwoot/chatwoot/pull/13904).
- Seat limit under concurrent creates: `402 Account limit exceeded. Please purchase more licenses` — [#15029](https://github.com/chatwoot/chatwoot/pull/15029).
- One `message_created` webhook per message despite duplicate provider deliveries — [#13523](https://github.com/chatwoot/chatwoot/pull/13523).
- Identity continuity: after an identifier rotation the next message lands on the same contact and conversation, no second contact — [#15357](https://github.com/chatwoot/chatwoot/pull/15357), [#15175](https://github.com/chatwoot/chatwoot/pull/15175); replies of merged contacts go to the right destination — [#15359](https://github.com/chatwoot/chatwoot/issues/15359).
- Import: re-running an import records already-imported items as skipped (no duplicates), history written without outbound delivery, stalled state reported by the API after 15 minutes, retry preserves progress — [#14922](https://github.com/chatwoot/chatwoot/pull/14922), [#15050](https://github.com/chatwoot/chatwoot/pull/15050).
- SLA: deadlines pre-computed by the back end with business hours; completion timestamp exposed "through REST and realtime payloads"; deletion returns immediately and cleans up asynchronously — [#13392](https://github.com/chatwoot/chatwoot/pull/13392), [#15024](https://github.com/chatwoot/chatwoot/pull/15024), [#12944](https://github.com/chatwoot/chatwoot/pull/12944).
- Reports: rollup-backed and raw-event-backed report responses must be identical ("Behavior is identical") — [#13798](https://github.com/chatwoot/chatwoot/pull/13798); reporting events queryable via API — [#12832](https://github.com/chatwoot/chatwoot/pull/12832).

- Uninstall: after the provider's deauthorize/uninstall webhook the integration and tokens are gone and status reads "disconnected" — [#16253](https://github.com/chatwoot/chatwoot/pull/16253), [#16084](https://github.com/chatwoot/chatwoot/pull/16084).
- API contract: responses validated against the OpenAPI spec in tests — [#13623](https://github.com/chatwoot/chatwoot/pull/13623), [#13693](https://github.com/chatwoot/chatwoot/pull/13693).
- Unread counts: counts per inbox/label/team/filter via `/unread_counts` — [#14369](https://github.com/chatwoot/chatwoot/pull/14369); the incident shows a load-shaped check (pool exhaustion) rather than a value check — [#14769](https://github.com/chatwoot/chatwoot/pull/14769).

### Inferences
- Suggested seeds, in order of fit for a ten-service benchmark (all behaviours, no code): (1) customer identity rotation/merge across commerce and desk with events arriving under old and new ids (from D); (2) historical backfill of orders/tickets with idempotent re-run, stall detection and no notification side effects (from G); (3) signed inbound webhooks rolled out without breaking existing senders, plus per-subscriber outbound secrets with backfill (from N); (4) exactly-once assignment with capacity under concurrent events (from H); (5) pre-aggregated reporting table with dual read path that must match raw results and a backfill (from O); (6) derived unread/order counters that must stay correct and cheap under burst load (from I); (7) SLA deadlines with business hours and frozen misses, notified by email/push (from J); (8) app-store-style install: uninstall/compliance webhooks, billing source per account (commerce vs payments) (from E/F).
