# Saleor feature-request history spanning core, dashboard, Stripe app, AvaTax app, SMTP app

Research date: 2026-11-15. Scope: saleor/saleor (core), saleor/saleor-dashboard, saleor/apps (Stripe, AvaTax, SMTP).

**How to read the evidence tags**

- `[web]` = the linked page was opened during this research (GitHub HTML page or unauthenticated GitHub search API).
- `[clone]` = fact read from the full-history local clones of the three upstream repositories (HEADs: saleor 2026-11-12, saleor-dashboard 2026-11-13, apps 2026-10-28). PR links with this tag are built from the `(#NNNN)` suffix of the squash-commit subject; **the PR web pages themselves were not opened**. Dates are commit dates on the default branch.
- Diff sizes are `git show --shortstat` of the squash commit. They **include generated GraphQL schema/types, snapshots and tests**, so they overstate hand-written code (worst cases are flagged).
- Vote counts: issue "+1" counts come from the GitHub search API (`reactions.+1`) on 2026-11-15; discussion upvotes are as rendered on the discussion list pages. Anything not confirmed is marked "unverified".

## 1. Which most-upvoted or longest-running feature requests and discussions span several of the five codebases?

### Takeaway
Upvotes are a weak signal in Saleor (the all-time top issue has 30 thumbs-up; almost every RFC has 0-3), and since February 2025 feature discussion has moved to Discord and a roadmap page that is currently offline, so "longest-running and still open" plus "number of codebases a design names" is a better ranking key than votes. The strongest multi-repository requests that upstream has **not** built are: buyer-aware price lists (#19380), payment requests / pay-by-link (#12976), programmatic charging of stored payment methods (#13401), checkout/order additional fees (#14031 → discussion #14470), multiple vouchers/gift cards per checkout (#14995), and cart-contents promotion conditions (#19796).

### Inferences
- Because votes are so low, the maintainers' own RFCs (authored by korycins, witoszekdev, lkostrowski, krzysztofwolski, maarcingebala) are the best proxy for "real demand"; rows 1-4 are all maintainer-authored and name three or more codebases.
- Rows 2, 3 and 4 are the only requests found whose text assigns distinct obligations to core, a payment app, a notification app and the dashboard at once; all three are unbuilt.
- Row 1 (price lists) is in tension with what upstream shipped six weeks later (customer types and customer attributes, B9) and with the April 2025 statement "we are making a choice not to build customer groups at all": the RFC introduces "Customer Tags" as a new grouping entity.

### Gaps
- saleor.io/roadmap is disabled and web.archive.org could not be fetched, so no roadmap items or roadmap vote counts could be collected.
- Discord (where requests have gone since Feb 2025) and the maintainers' Linear tracker are not publicly indexable; requests raised only there are missing.
- Reaction counts on #19380, #19796 were not rendered on the fetched pages (API search listed +0 at the time).
- docs.saleor.io upgrade guide URL guessed (`/upgrade-guides/3-22-to-3-23`) returned 404; upgrade guides were not reviewed. Release notes were read from the in-repo `CHANGELOG.md` at tags 3.21.0, 3.22.0, 3.23.0 and HEAD instead.

## 2. For requests that were built: PRs per repository, order, time span, follow-up fixes and reverts

### Takeaway
Built cross-repository features in 2025-2026 follow a consistent shape: a large core PR lands first, the dashboard and each app follow weeks to months later (20 months for the circuit-breaker UI), and the apps gate behaviour on the Saleor version — which is exactly where the observed regressions occurred (SMTP webhooks rejected on 3.22, Stripe payment-method details silently dropped on 3.23). Since 2026-09-17 the public saleor/apps history consists of "Sync from internal repository" commits, so per-PR history for apps after that date is only visible through per-app CHANGELOG entries.

## 3. For requests still open or abandoned: maintainers' stated reasons

### Takeaway
Maintainers rarely say "no"; most cross-repository requests die from silence (stale-bot, backlog cleanup, migration to Linear) or stay as unfinished drafts with explicit unresolved contract questions. The few stated reasons are consistent: avoid special-purpose entities that must be supported forever, keep Saleor from sending notifications or scheduling charges itself, and leave provider-specific behaviour to apps.

### Cited Findings
- Customer groups: "So we are making a choice not to build customer groups at all"; user attributes proposed instead; "we are super careful about adding new code because realistically it will stay with us for months"; customer attributes "would apply only at checkout and order level, not to catalogue promotions"; requester replied they would fork — [web #17600](https://github.com/saleor/saleor/issues/17600)
- Price lists (open): tag-scoped prices "are calculated at read time" so "catalog sort and filter do not reflect per-buyer tag prices"; buyer identity "is determined on the server, not taken from the request body"; explicitly out of scope: quantity tiers, per-country prices, B2B company accounts, bulk mutations, legacy plugin hooks, CSV import — [web #19380](https://github.com/saleor/saleor/issues/19380)

- Stored payment methods RFC: deferred or removed the Transaction↔PaymentMethod link ("will be discussed further in the future"), `User.defaultPaymentMethod`, and expiry notifications ("none of the payment providers we support sends a notification before the card expires"); subscription scheduling: "No, this interval wouldn't be managed by Saleor itself" — [web #12843](https://github.com/saleor/saleor/issues/12843)

## 4. RFCs or design discussions that show disagreement about where logic should live (core vs. app vs. dashboard)

### Takeaway
The recorded disagreements cluster around four boundaries: (a) what core must put in a sync-webhook payload so an app can stay stateless (tax discounts, refund lines, idempotency keys); (b) whether app health/log state belongs in core storage, app metadata or dashboard presentation; (c) whether customer segmentation is a first-class core entity or generic attributes; (d) snapshot-at-trigger vs state-at-delivery for webhook payloads. An accepted decision record states the general rule: no new features in plugins, integrations go to apps, and "Attributes are for people, metadata are for apps."

### Cited Findings
- Decision record 001 (Accepted): "we do not build any new features in these plugins"; Stripe plugin → "Open-source app replacement in progress"; Avatax → "App replacement available"; SendGrid and user_email → SMTP app; admin_email and webhook "Folded into core" — [web: decision-records 001](https://github.com/saleor/decision-records/blob/main/decisions/001_plugins_apps_direction.md)
- Decision record 003 (Accepted): "Attributes are for people, metadata are for apps"; attributes only "where it makes sense to have data with a strict schema"; metadata validation "should happen in the app's unit tests" — [web: decision-records 003](https://github.com/saleor/decision-records/blob/main/decisions/003_attributes_vs_metadata.md)
- Decision record 004 (Accepted): from 3.22 `<entity>Update` fires "only for non-metadata changes"; metadata changes fire `<entity>MetadataUpdate`; "a flag will be introduced to retain the current behavior" — [web: decision-records 004](https://github.com/saleor/decision-records/blob/main/decisions/004_update_webhook_behavior_unification.md)
- AvaTax vs manual discounts: "The Avatax app does not have enough information on how to distribute order-level discounts"; core adds `type` (`SUBTOTAL`/`SHIPPING`) and splits the manual discount; a reviewer wanted "hard references" (voucher and discount) on `TaxableObjectDiscount` because names are not unique or translatable — unanswered — [web #16613](https://github.com/saleor/saleor/issues/16613)
- Tax-app failure handling: reviewers asked for docs on "what makes an invalid and successful response (status codes etc.)", for `taxAppId` to be required on new mutations, a strategy union "AppTaxStrategy | PluginStrategy | FlaxRateStrategy", and "let's convert all 4xx and 5xx to TaxAppProblem" — [web #12942](https://github.com/saleor/saleor/issues/12942)
- App logs: korycins wanted a "mark as resolved" mutation or "the dashboard will keep showing solved errors"; lkostrowski: "Logs is immutable event.
