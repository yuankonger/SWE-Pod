## 1. Transactions API evolution: which core changes forced app changes, broke apps, or changed semantics without changing shape?

### Takeaway
The contract between core and a payment app is mostly *behavioural*: de-duplication by `(transaction, type, pspReference)` plus amount, pairing of `*_REQUEST` with later `*_SUCCESS/FAILURE` by `pspReference`, events without `pspReference` being excluded from amount calculation, `actions` being advisory, and time-ordered (not arrival-ordered) failure precedence. Core changed these rules repeatedly in patch releases (3.19–3.23), often backported to 2–3 branches, and the Stripe app encodes each rule in its own code (pspReference choice, amount choice, timestamp choice, `actions` lists, handling of `alreadyProcessed`).

### Cited Findings

Contract rules as documented today (docs stamped Saleor 3.23.43)

- De-duplication: "If there is an event with the same `pspReference`, `amount`, and `type` … Saleor will return it instead of creating a new one, and the flag [`alreadyProcessed`] will be set to `true`"; same pspReference+type with a different amount → `INCORRECT_DETAILS`; a second `AUTHORIZATION_SUCCESS` → `ALREADY_EXISTS` ("Use `AUTHORIZATION_ADJUSTMENT`"). `AUTHORIZATION_ACTION_REQUIRED`, `CHARGE_ACTION_REQUIRED`, `INFO` are never de-duplicated. "Deduplication is done within single `TransactionItem`." — [Transactions docs](https://docs.saleor.io/developer/payments/transactions), [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle). Verified in code: `get_already_existing_event` filters on `transaction_id, psp_reference, type` under `select_for_update` and the mutation branches on amount equality — [saleor/payment/utils.py](https://github.com/saleor/saleor/blob/main/saleor/payment/utils.py), [transaction_event_report.py](https://github.com/saleor/saleor/blob/main/saleor/graphql/payment/mutations/transaction/transaction_event_report.py).
- To correct a wrong amount: "Previous event must be invalidated via `_FAILURE` event, then report `_SUCCESS` event again, new `_SUCCESS` event must have **different pspReference**." — [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle)
- Request/response pairing: "The `pspReference` will be placed in the previously created event of `…_REQUEST` type"; "If a `REFUND_SUCCESS` event is related to a `REFUND_REQUEST` event by `pspReference`, then … `refundPendingAmount` will be reduced … If there is no related `REFUND_REQUEST` event, the provided `amount` will reduce `transaction.chargedAmount`." — [Transactions docs](https://docs.saleor.io/developer/payments/transactions)
- Missing pspReference: "the event will still be created but will be excluded from transaction amount recalculations". — [Transactions docs](https://docs.saleor.io/developer/payments/transactions)
- Failure precedence is by event `time`: an event is excluded "if it has matching `*_FAILURE` event with the same `pspReference` and newer `time`"; "New events can be reported to Saleor in non-subsequent order." — [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle)
- `actions` are not enforced by core: "Saleor Transaction model **is not a state machine**"; available actions "are honored by Saleor Dashboard, but are not rejected once `transactionRequestAction` is requested via API … such validation is on the Payment App side." — [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle)
- Checkout vs order asymmetry: "pending amounts are included in Checkout `authorizeStatus` calculation, but are not considered in Order `authorizeStatus` calculation." — [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle)
- Core auto-creates `_FAILURE` events without pspReference "when handling incorrect response from sync webhook sent to payment app (e.g. app didn't respond in 20s, returned JSON is invalid, etc.)". — [Lifecycle docs](https://docs.saleor.io/developer/payments/lifecycle)
- The Stripe app delegates de-duplication to core: "App itself doesn't de-duplicate - Saleor does. In case of duplicated event, the app will resolve the same result (PSP Reference, amount, type) and report it to Saleor again. Saleor will reject this event with an ALREADY_REPORTED error, which the app gracefully handles." — [Stripe app docs](https://docs.saleor.io/developer/app-store/apps/stripe/overview). Verified in code: the reporter maps both the `ALREADY_EXISTS` error code and `alreadyProcessed: true` to `AlreadyReportedError`, and maps `INCORRECT_DETAILS`, `INVALID`, `NOT_FOUND`, `REQUIRED` to an unhandled error — [transaction-event-reporter.ts](https://github.com/saleor/apps/blob/main/apps/stripe/src/modules/saleor/transaction-event-reporter.ts).

### Inferences
- The rules that the first (too easy) task exercised — refund events must carry the refund id, core de-duplicates on `(type, pspReference)` — are one row of a larger table of *paired* rules. Each of the following needs knowledge from both sides to get right: (a) which Stripe object id is the pspReference for each event type, (b) which Stripe amount field (`amount`, `amount_capturable`, `amount_received`) corresponds to the amount core expects for de-duplication (amount mismatch = `INCORRECT_DETAILS`, not `alreadyProcessed`), (c) which timestamp is reported (failure precedence is by `time`), (d) whether a missing pspReference removes an event from the calculation.
- Several core fixes were backported to 2–3 branches under different PR numbers within days; a faithful "company" would have the app owner needing to know *which patch version* of core it is talking to, not just the minor.

### Gaps
- Most PR web pages for the core PRs in the table were not opened; descriptions come from commit messages and changelogs. Those that were opened are quoted in section 3 (I1–I15), and the numbers in this table are the `main` ports, not always the original PR. Core commit bodies are often empty (e.g. #17002, #15110, #18642), so the *motivating app incident* is not recorded publicly for most of them.
- Chargeback/dispute handling: core supports `CHARGE_BACK` and `REFUND_REVERSE` events (docs above); I found **no** handling of Stripe disputes in the Stripe app (subscribed Stripe events are only `payment_intent.*` and `charge.refund.updated` per the [app webhooks docs](https://docs.saleor.io/developer/app-store/apps/stripe/overview)) and no issue/PR about it. No cross-repo case exists here — it is a capability gap.
- Stored payment methods / tokenization: the Stripe app does not implement them (migration page: "Saving payment method in Stripe … Not supported"); core-side history exists ([#13581](https://github.com/saleor/saleor/pull/13581), [#13660](https://github.com/saleor/saleor/pull/13660), [#13879](https://github.com/saleor/saleor/pull/13879), [#13794](https://github.com/saleor/saleor/pull/13794), [#18373](https://github.com/saleor/saleor/pull/18373)) but no Stripe-app counterpart.
- Partial capture: app docs state "One authorized amount can only be captured once (either fully or partially). Multiple captures are not supported." No bug history found.

## 2. Stripe app issues and PRs whose root cause was a mismatch with core

### Takeaway
The app's history contains at least nine verified cases where the app was wrong or incomplete because of something only core could tell it (pspReference rules, amounts, actions, version strings, webhook subscription state, app identity, permission model). The most instructive are the semver version gate (latent for a year, triggered by a *core upgrade*, fixed 2026-10), the idempotency-key rollout (needs a core patch release, an app release and a webhook-subscription migration, in that order), and refund identity (refund id vs payment-intent id).

### Cited Findings

**C1 — Co-development cluster, May 2025: cancel amount, response amounts, event time, validation (core 3.21 ↔ Stripe app pre-release)**
- Core, 2025-05-07→09: #17676 (3.20) "Enhance `TransactionEvent` handling and add `createdAutomatically` field" then same-day revert #17682 "Revert adding createdAutomatically to TransactionEvent type"; main [#17681](https://github.com/saleor/saleor/pull/17681) ("Ensure that request event is updated with all response data … Revert adding createdAutomatically flag"); [#17690](https://github.com/saleor/saleor/pull/17690) "Set amount as optional in transaction webhook flow"; [#17691](https://github.com/saleor/saleor/pull/17691); [#17693](https://github.com/saleor/saleor/pull/17693) "Ensure that transaction event time is properly transformed to UTC". Verified (commit).
- App, same days: cancel support [apps#1907](https://github.com/saleor/apps/pull/1907) (2025-05-07); refunds [apps#1911](https://github.com/saleor/apps/pull/1911) (05-08); "Sync resolving amounts from PaymentIntent in Stripe app" (commit [7346a49b](https://github.com/saleor/apps/commit/7346a49b), 05-09); "Fixes after refund PR" [apps#1915](https://github.com/saleor/apps/pull/1915) (05-09); "Send canceled_at time in Saleor webhooks" [apps#1918](https://github.com/saleor/apps/pull/1918) (05-13); "Bump Stripe to 3.21" [apps#1935](https://github.com/saleor/apps/pull/1935) (05-23). Verified (diff for 7346a49b, #1918).
- What the app encodes: amount by intent status — `canceled/requires_payment_method/requires_action/processing → amount`, `requires_capture → amount_capturable`, otherwise `amount_received` ([resolver](https://github.com/saleor/apps/blob/main/apps/stripe/src/modules/saleor/resolve-saleor-money-from-stripe-payment-intent.ts)); time — for a cancelled intent `canceled_at`, otherwise `null` with the code comment "For other statuses, Stripe sends us the PaymentIntent created date - which don't use to avoid raporting events from the past instead of the current date of the webhook event" (#1918 diff).
- Core side of the same facts: "Previously, the `action.amount` field in the `TransactionCancelationRequested` subscription … was always set to `null`. Starting with Saleor 3.21, this field will contain the amount requested by the user…" — [3.20→3.21 guide](https://docs.saleor.io/upgrade-guides/core/3-20-to-3-21).
- Symptom vs cause: wrong `time` or amount on the app side shows up in core as an event that is ignored in calculation or rejected as `INCORRECT_DETAILS`; cause is the mapping in the app, but the rule lives in core.

**C2 — Refund identity: refund events must use the Stripe refund id (`re_…`), not the payment intent id (`pi_…`)**
- App: "Add refunds to Stripe app" [apps#1911](https://github.com/saleor/apps/pull/1911) (2025-05-08) → "Fixes after refund PR" [apps#1915](https://github.com/saleor/apps/pull/1915) (05-09) → "Add support for multiple refunds in Stripe" [apps#1922](https://github.com/saleor/apps/pull/1922) (05-13). Verified (diff): #1922 changes `RefundSuccess/Failure/Request` results from `pspReference: this.stripePaymentIntentId` to `this.stripeRefundId`, adds `resolvePspReference()` switching on `REFUND_*`, and introduces a special `TransactionRefundRequestedFailureResult` with the comment "Special case - we don't have a refund id yet, so we can't create a RefundFailureResult".
- Why only core could tell: with the intent id as pspReference, the second `REFUND_SUCCESS` on the same transaction matches the first in `get_already_existing_event` → `alreadyProcessed` (same amount) or `INCORRECT_DETAILS` (different amount). Three PRs in five days.
- Residual asymmetry: a refund that fails synchronously has no refund id, so its failure event carries the payment-intent id — and per core docs "`*_FAILURE` … amount is taken from the corresponding `*_SUCCESS` or `*_REQUEST` event with the same `pspReference`".
- Later hardening, app only: "Set metadata during refund creation / Ignore events with missing metadata" [apps#2035](https://github.com/saleor/apps/pull/2035) (2025-07-24), "Fix Stripe PaymentIntent metadata not being passed to API" [apps#2072](https://github.com/saleor/apps/pull/2072) (2025-09-01, "Fixes webhook processing failures due to missing Saleor metadata in PaymentIntents").

**C3 — `actions` returned by the app**
- "Fix result actions for processing payment intent in Stripe" [apps#1921](https://github.com/saleor/apps/pull/1921) (2025-05-13): `actions = ["CANCEL"]` → `[]` for two result classes. Verified (diff).
- "Fixed missing actions for TransactionInitializeSession. After this change staff user can cancel transaction even if there is no payment made but payment intent has been created." — app CHANGELOG 2.0.4, [apps#1979](https://github.com/saleor/apps/pull/1979) (2025-06-17), found when the app started generating TypeScript types from core's published JSON schemas (core [#17752](https://github.com/saleor/saleor/pull/17752) 2025-05-28, [#17760](https://github.com/saleor/saleor/pull/17760) 2025-06-09, [#17815](https://github.com/saleor/saleor/pull/17815)).
- Symptom vs cause: the *dashboard* hides the Cancel/Refund button (it honours `actions`), core does not enforce them; cause is the app's list.

**C4 — Payment method details: version gate written with a semver range that excluded the next minor  [fix is POST-JUNE-2026]**
- Core 3.22: [#17845](https://github.com/saleor/saleor/pull/17845) (2025-06-23) adds `paymentMethodDetails` to `transactionEventReport` and to initialize/process responses.
- App 2.3.0: [apps#2103](https://github.com/saleor/apps/pull/2103) (2025-10-15) sends details, "only available for Saleor 3.22+ … Version compatibility check using `SaleorVersionCompatibilityValidator`". The reporter uses two different GraphQL documents (`TransactionEventReportWithPaymentDetailsDocument` vs `TransactionEventReportDocument`) so that older cores do not reject an unknown argument.
- The gate: `new SaleorVersionCompatibilityValidator("3.22").isSaleorCompatible([major, minor])` → `semver.satisfies("3.23.0", "3.22")` — in semver a bare `3.22` is the range `3.22.x`, so 3.23 fails. Verified (code): [saleor-version-compatibility-validator.ts](https://github.com/saleor/apps/blob/main/packages/shared/src/saleor-version-compatibility-validator.ts) and the removed lines in sync commit [3601e299](https://github.com/saleor/apps/commit/3601e299).
- The version checked is not live: it is `saleorSchemaVersion` stored in the app's DynamoDB `RecordedTransaction` at `transactionInitializeSession` time. **C5 — Idempotency of charge/refund/cancel requests  [POST-JUNE-2026]**
- Core [#19811](https://github.com/saleor/saleor/pull/19811) (main, 2026-09-23) and #19813 (3.23, first in tag 3.23.36 of 2026-09-24): "`handle_transaction_request_task` re-sends the same `EventDelivery` on any 5xx (up to 5 retries) and the broker can redeliver it on a pod kill, so an app could receive the same refund request several times with nothing in the payload to recognise the duplicate." The key is the already-stored `TransactionEvent.idempotency_key` of the request event. "Known gap, deliberately not addressed here: a timeout never produces a 5xx, so it never retries. The merchant's manual re-issue via `transactionRequestAction` mints a fresh key and the app acts again. Closing that needs a client-supplied idempotency key argument, which is its own change." Verified (commit body).
- App 2.10.0 (public sync commit [a3c91997](https://github.com/saleor/apps/commit/a3c91997), 2026-09-29): adds `idempotencyKey` to the three subscription queries and forwards it to `refunds.create`, `paymentIntents.capture`, `paymentIntents.cancel`. Changelog: "a retry that arrived after Stripe had already accepted a refund created a second, duplicate refund … Two separate refunds of the same amount are still processed independently, because Saleor assigns each requested action its own key. Requires Saleor 3.23 or newer". Verified (diff).
- Rollout knowledge embedded in app code: "Installations that didn't migrate their webhook subscription query yet don't send it. In that case Stripe SDK generates its own key, which only covers retries within a single request - the pre-3.23 behavior." and the warning "Webhook subscription query is outdated - run webhooks migration" ([transaction-requested-event-helpers.ts](https://github.com/saleor/apps/blob/main/apps/stripe/src/modules/saleor/transaction-requested-event-helpers.ts)). The app's own rollback cancel of an orphaned intent passes `idempotencyKey: undefined` ("Best-effort rollback, not a Saleor-requested action").
- Version precision: the field exists only from 3.23.36; docs badge says "Added in Saleor 3.23" ([API reference](https://docs.saleor.io/api-reference/payments/objects/transaction-refund-requested)); the app manifest says `requiredSaleorVersion: ">=3.23 <4"`. ## 4. Rollout-order cases: who ships first, version gates, webhook subscription migrations, backfills

### Takeaway
There is no general "update apps before core" rule in the upgrade guides; ordering constraints are scattered through app changelogs and code comments. The real constraints are: (1) `requiredSaleorVersion` is enforced only at install time; (2) a new field in a subscription query takes effect only after the app's webhook migration rewrites the subscription stored in core, and fails if core's schema lacks the field; (3) new permissions are not granted to existing installations automatically; (4) the app keeps per-transaction state (including the core version at creation time) that outlives upgrades.

### Cited Findings

**R1 — `requiredSaleorVersion` floor moves and what they do not cover**
- Floors: `>=3.21` ([apps#1935](https://github.com/saleor/apps/pull/1935), 2025-05-23) → `>=3.22 <4` ([apps#2433](https://github.com/saleor/apps/pull/2433), 2026-09-03, app 2.8.0) → `>=3.23 <4` (app 2.9.0, sync commit [602c0cbf](https://github.com/saleor/apps/commit/602c0cbf), 2026-09-22). **[POST-JUNE-2026]**
- "installing on an older Saleor will be rejected by the Dashboard. Saleor 3.22 users should stay on the previous app release until they upgrade their Saleor instance." — [app CHANGELOG 2.9.0](https://github.com/saleor/apps/blob/main/apps/stripe/CHANGELOG.md). The check is at install; a hosted app that redeploys serves already-installed older cores.
- Core sends its version via the `Saleor-Schema-Version` header since [#13075](https://github.com/saleor/saleor/pull/13075) (2023-06-19); the Stripe app persists it per transaction (C4).
- GraphQL schema snapshot in the app is refreshed by scheduled "Update GraphQL schema" PRs (e.g. [apps#2241](https://github.com/saleor/apps/pull/2241) to 3.22 on 2026-02-23, [apps#2302](https://github.com/saleor/apps/pull/2302) to 3.23 on 2026-03-31) — codegen validates against the newest schema, not the oldest supported one (see CH9).

**R2 — Idempotency key: core patch → app release → webhook migration** (C5). Order: core 3.23.36 (2026-09-24) → app 2.10.0 (2026-09-29) → `scripts/run-webhooks-migration.ts` run on deploy for every installation in the APL ([script](https://github.com/saleor/apps/blob/main/apps/stripe/scripts/run-webhooks-migration.ts)). Until the last step the payload has no key and the app silently falls back to non-idempotent behaviour with a warning log.

**R3 — Order number in Stripe metadata: new permission + new webhook for existing installations  [POST-JUNE-2026]**
- 2.12.0 (sync commit [8aad969e](https://github.com/saleor/apps/commit/8aad969e), 2026-10-19): `saleor_order_id`, `saleor_order_number`, `saleor_checkout_id` metadata on intents and refunds; "Order details are added after the app's webhooks are migrated, which happens on the app's deployment." "Payments captured right away during checkout still don't have the order number, because the order doesn't exist yet when Stripe creates the payment."
- 2.15.0 (sync commit [f001ac7e](https://github.com/saleor/apps/commit/f001ac7e), 2026-10-28): subscribes to `ORDER_CREATED`; "This needs the new 'Manage orders' permission. New installations get it automatically. For existing installations, the configuration page shows a banner that asks a staff member with the 'Manage apps' permission to grant it. After it's granted, the app turns the feature on by itself."
- Code: manifest `permissions: ["HANDLE_PAYMENTS", "MANAGE_ORDERS"]` with comment "MANAGE_ORDERS is needed for ORDER_CREATED. Installations from before it was added request it from the app UI"; `OrderSyncInstaller` checks permission, then creates the webhook itself, caching only the enabled state ("A missing permission is always checked again, because staff can grant it at any moment and Dashboard reloads the app right after") — [order-sync-installer.ts](https://github.com/saleor/apps/blob/main/apps/stripe/src/modules/order-sync/order-sync-installer.ts). The handler filters `order.transactions` by `createdBy.id === appId` and `pspReference.startsWith("pi_")` — [use-case.ts](https://github.com/saleor/apps/blob/main/apps/stripe/src/app/api/webhooks/saleor/order-created/use-case.ts).
- Core facts the app depends on: transactions move from checkout to order at completion; `Order.transactions` is not filtered per app (gift-card gateway since 3.23); `createdBy` returns the *active* app ([#14933](https://github.com/saleor/saleor/pull/14933)); since 3.23 `ORDER_*` async payloads are built by a background task and "can carry the state after the second change" ([3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23)); 3.24 removes `MANAGE_APPS` from apps ([3.23→3.24 guide](https://docs.saleor.io/upgrade-guides/core/3-23-to-3-24)), so the app cannot grant itself the permission — a staff user in the dashboard must.
- Three parties: app (feature), core (permission/webhook model), dashboard (banner + grant UI inside the app iframe).

**R4 — Core data migrations that touch existing transactions**
- Upgrade guides require "first migrating to the latest 3.22.x release and enabling the Celery worker to process all data migrations asynchronously" — [3.22→3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23) (same banner in every guide since 3.16→3.17).
- Examples on the payment path: [#14870](https://github.com/saleor/saleor/pull/14870) (checkout `last_transaction_modified_at`/refundable backfill, `checkout/migrations/tasks/saleor3_14.py`); [#15000](https://github.com/saleor/saleor/pull/15000) (idempotency field + index migrations landed a week before the logic, [#15010](https://github.com/saleor/saleor/pull/15010)); #17878 (channel funds-release setting, "move data migration to celery task", "change cut-off-date to be dependent on creation date"); [#12237](https://github.com/saleor/saleor/pull/12237) "Add zero-downtime support for support-refund" (2023-03-27); order status backfill [#12083](https://github.com/saleor/saleor/pull/12083).
- Payment method details are not backfilled: "Transactions created before 3.22 will not have these new details." "Payment method filtering only works for transactions created after upgrading" — [3.22.0 release](https://github.com/saleor/saleor/releases/tag/3.22.0), 3.22 CHANGELOG.

**R5 — Behaviour switches defaulted differently for new vs existing instances**
- Automatic checkout completion: "disabled for existing instances by default … New Saleor instances created from version 3.20 onwards will have this feature enabled by default" — [3.19→3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20). With it on, the Stripe webhook's `transactionEventReport` creates the order, and `checkout(id)` returns `null` to a storefront still waiting to call `checkoutComplete`.
- New channels default to `MarkAsPaidStrategyEnum.TRANSACTION_FLOW` from 3.21; the Stripe app's configuration docs require "Use Transaction flow when marking order as paid" on the channel.
- 3.22: "webhooks are no longer triggered for deactivated apps" — [3.21→3.22 guide](https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22).

**R6 — Plugin → app migrations demanded before a core upgrade**
- Legacy Stripe plugin: "Stripe (Deprecated)" removed in 3.21; "Stripe Plugin has been deprecated … Please use the Stripe App" in 3.22 CHANGELOG; legacy Payments API deprecated [#19477](https://github.com/saleor/saleor/pull/19477) **[POST-JUNE-2026]**; Dummy/Razorpay/Braintree/Authorize.net plugins removed for 3.24 ([#19551](https://github.com/saleor/saleor/pull/19551), [#19552](https://github.com/saleor/saleor/pull/19552), [#19554](https://github.com/saleor/saleor/pull/19554), [#19142](https://github.com/saleor/saleor/pull/19142)); "Stop using the plugin before upgrading." — [3.23→3.24 guide](https://docs.saleor.io/upgrade-guides/core/3-23-to-3-24). The Stripe app has a "migration from plugin" docs page listing unsupported plugin features.

**R7 — App storage migrations (app-internal, but gate what the app can answer about old transactions)**
- DynamoDB APL moved local → shared package → app-sdk: [apps#1884](https://github.com/saleor/apps/pull/1884), [apps#2000](https://github.com/saleor/apps/pull/2000), [apps#2043](https://github.com/saleor/apps/pull/2043); "`APL=saleor-cloud` is no longer accepted … the Stripe app quietly saved auth data to a local file instead" (2.13.0, Oct 2026 **[POST-JUNE-2026]**); encryption key rotation [apps#2315](https://github.com/saleor/apps/pull/2315). `RecordedTransaction` rows "have no TTL and stay in DynamoDB forever" (C4).

### Inferences
- R2 has a hidden fourth precondition not stated anywhere: an installation on 3.23.0–3.23.35 satisfies the manifest floor but its schema has no `idempotencyKey` on the three payload types; the webhook migration's `webhookUpdate` with the new query would presumably be rejected for it (as happened to the SMTP app in CH9), leaving it on the old subscription and the warning path. Not confirmed by any source.

### Gaps
- No explicit feature flags on the payment path between core and the Stripe app were found (the dashboard's `improved_refunds` flag, removed in 3.22, is dashboard-side).
- I did not find a public statement of the hosted Stripe app's deploy cadence relative to Saleor Cloud core upgrades.
