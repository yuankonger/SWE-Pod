## 1. Zero-downtime migration practice: the documented rules and the real PRs where a migration broke, locked, was slow or had to be rewritten

### Takeaway
Saleor has an explicit, multi-release expand/contract policy (old code must run on the new schema; no lock longer than one second; column removal and type changes spread over 2 to 5 minor versions; long data migrations run as self-re-queuing Celery tasks fired from `post_migrate`), and the upgrade guides make "be on the latest patch of the previous minor with a Celery worker running" the precondition for a no-downtime upgrade. The history shows the policy failing in recurring, specific ways: tasks that were never registered with Celery (so the data migration silently did nothing and needed a *new* migration to re-fire), tasks that deadlocked with live checkout traffic, migrations that had to be converted back from async to sync, and backports that needed different migration numbers plus merge migrations per branch.

### Cited Findings

**The documented rules**

- The policy's two goals: old code must work with the new schema (or vice versa), and "Migrations don't lock tables, rows etc. for no longer than one second." [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Adding a non-nullable field is a two-minor process: version X-1 adds it nullable, writes it from code and back-fills it with a migration task; version X makes it non-nullable. Django does not set DB defaults, so a `RunSQL ... SET DEFAULT` is required for old code to keep inserting rows. [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Renaming a field: X-1 adds the new field, **writes both**, back-fills; X reads only the new one; later the old one is removed by the removal procedure. [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Changing a field's type without renaming spans five minors (X-1 … X+3) via a temporary field with dual writes in both directions (documented example: `number` int → string via `number_string`, 3.22 → 3.25). [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Removing a field: version X removes it from the ORM only (`SeparateDatabaseAndState`, column made nullable/defaulted); version X+1 drops the column with `RunSQL` + `reverse_sql`. [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Indexes must use `AddIndexConcurrently`/`RemoveIndexConcurrently` in an `atomic = False` migration and "Please don't use nonatomic for other migrations"; FK indexes must be split out from the FK migration. [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- Data migrations: never run long work in the migration; put a task in `saleor/<module>/migrations/tasks/saleor<X>.py`, trigger it by connecting to `post_migrate` inside a `RunPython`, and the task must run under one second per execution, be idempotent, check for remaining work, be safe with concurrent workers without deadlocking, re-queue itself, and process newest-to-oldest. The task package **must be registered** in `saleor/celeryconf.py` (`app.autodiscover_tasks(packages=[...], related_name="saleor3_24")`). [W] — [Zero-downtime migrations](https://docs.saleor.io/developer/community/zero-downtime-migrations)
- The in-repo agent/contributor rules add: migration tasks go on a dedicated queue (`@app.task(queue=settings.DATA_MIGRATIONS_TASKS_QUEUE_NAME)`), lock rows first with `select_for_update` and update in a second query, stop chaining on an empty batch; unique constraints must be built with `CREATE INDEX CONCURRENTLY` in their own non-atomic migration and attached with `ADD CONSTRAINT ... USING INDEX` inside `SeparateDatabaseAndState`. [L] `AGENTS.md` at `6f714faf` — [AGENTS.md](https://github.com/saleor/saleor/blob/main/AGENTS.md)
- Backport rule: start on the lowest affected version, then cherry-pick upward and add `makemigrations --merge` on each higher branch and on `main`; every migration must be reversible (`RunPython.noop` at minimum). [L] — [CONTRIBUTING.md](https://github.com/saleor/saleor/blob/main/CONTRIBUTING.md)
- Upgrade guides repeat one ordering rule for every minor: "It is recommended to first migrate to latest 3.20.X" and "turn on the Celery worker to process all data migrations asynchronously", "Otherwise, you will need to downtime your solution to ensure correct data migration." [W] — [3.20 → 3.21 guide](https://docs.saleor.io/upgrade-guides/3-20-to-3-21) (this URL, without `/core/`, is the one that resolved; the other guides resolve only under `/upgrade-guides/core/`), [3.19 → 3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20), [3.22 → 3.23 guide](https://docs.saleor.io/upgrade-guides/core/3-22-to-3-23). The guides do not name which tasks to wait for.
- 3.19 → 3.20 adds a pre-upgrade infrastructure step: "Make sure `PRIVATE_FILE_STORAGE` is configured properly in `settings.py` before upgrade", because webhook event payloads moved from the database to files in private storage. [W] — [3.19 → 3.20 guide](https://docs.saleor.io/upgrade-guides/core/3-19-to-3-20)

### Inferences
- The single most repeated failure is "migration applied, task never executed": `post_migrate` calls `.delay()` on a task whose module is not in `celeryconf.py` (or whose queue has no consumer). Because the migration is already recorded as applied on every deployed environment, the fix is always a *new* migration that re-fires the task, with the old one hollowed out. Wrong order (deploying the code fix without the re-fire migration, or running migrations before workers have the new code) leaves data permanently un-back-filled with no error.
- Migration tasks and live request handlers share row locks; three separate deadlock fixes (2023, 2024, 2026) show that a back-fill written without the request path's lock ordering will deadlock under production traffic but never in tests.
- Renaming a Celery task or moving its module is itself a compatibility event (queued messages and beat entries carry the old name), which is why #14711 pins an explicit task name.
- Per-branch migration numbering means a "backport" is not a cherry-pick: each branch gets its own number and a merge migration, and three different PR numbers.

### Gaps
- No public post-mortem naming an outage duration or customer impact was found for any migration case; "caused downtime" is stated only generically on the policy page. The link between a specific fix PR and a specific production incident is inferred from timing and titles.
- PR descriptions for #18670/#18671 do not state the cause; "task not registered in celeryconf" is inferred from the 3.22 PR title and diff.
- The upgrade guides never list which data-migration tasks must finish before the next minor; no tooling for checking completion was found.
- `https://docs.saleor.io/upgrade-guides/core/3-21-to-3-22` appears to carry a copy-pasted callout ("migrate to latest 3.20.X"); the intended text is presumably 3.21.X. Not confirmed.

## 2. Breaking changes and deprecations across 3.14 → 3.24: which needed apps/dashboard to move first or to support both behaviours

### Takeaway
Saleor ships most behaviour changes behind per-channel or per-shop "legacy" flags that default to the old behaviour on existing installations and the new one on fresh ones, and removes API surface only one or two minors after deprecating it. The changes that genuinely forced an ordered, multi-repository rollout are: transaction-API field removals (3.15), NOTIFY_USER deprecation (3.16), sales → promotions (3.17), webhook retry semantics (3.18), tax-app selection that can block checkout (3.19), automatic checkout completion and payload file storage (3.20), sync-webhook circuit breaker and bulk-query webhook suppression (3.21), deactivated-app webhook suppression and plugin deprecations (3.22), deferred payloads, AppExtension reshape and explicit delivery options (3.23), and the 3.24 removals that the dashboard and apps had to stop querying beforehand.

### Cited Findings

**3.15 (2023-08-25)**

- Removed the transaction-API surface deprecated in 3.13, including the `TRANSACTION_ACTION_REQUEST` webhook event (replaced by `TRANSACTION_CHARGE_REQUESTED`/`REFUND_REQUESTED`/`CANCELATION_REQUESTED`), `TransactionItem.status/type/reference/voidedAmount`, `TransactionActionEnum.VOID`. A payment app still subscribed to the old event stops receiving action requests. [L] changelog at tag 3.20.0 — [#13020](https://github.com/saleor/saleor/pull/13020)
- Introduced the `Saleor-Schema-Version` HTTP header on manifest fetch and install handshake (#13075); `requiredSaleorVersion` in the manifest dates from 3.13 (#12164) and is validated in `appInstall`/`appFetchManifest`. [L] — [#13075](https://github.com/saleor/saleor/pull/13075), [#12164](https://github.com/saleor/saleor/pull/12164)
- Checkout country resolution order changed (shipping address → billing → channel default), explicitly flagged as affecting the country used for tax calculation. [L] — [#13159](https://github.com/saleor/saleor/pull/13159)

**3.16 (2023-09-21)**

## 3. Webhook-delivery changes (deferred payloads, replica lag, retries, breaker, tracing)

### Takeaway
Webhook delivery semantics changed four times in ways that receivers can observe: retries stop on 4xx (3.18), payloads move to files (3.20), payloads are generated *after* the request from current state (checkout events in 3.21, order events in 3.23), and a per-webhook opt-out arrives only in a late 3.23 patch after integrations broke. The deferred mechanism itself needed a revert and re-land because of read-replica lag and Aurora incompatibility.

### Cited Findings

- ADR 0011 states the accepted consequence: "an async webhook is a notification that something happened, carrying the object's current state, not a snapshot … Two mutations in quick succession produce two deliveries that are indistinguishable to the receiver. If the object is deleted before the task runs, the deliveries are marked `FAILED` and no webhook is sent." Legacy (non-subscription) webhooks still serialise inline, so "The same event can reach a legacy receiver with `A` and a subscription receiver with `B`." **[POST-JUNE-2026 document]** [L] — [ADR 0011](https://github.com/saleor/saleor/blob/main/docs/adr/0011-deferred-webhook-payloads-reflect-state-at-generation-time.md)
- Rollout table from the ADR: `CHECKOUT_CREATED/UPDATED` deferred since 2024-11-15 (3.21.0, #16999); eleven `ORDER_*` events, `DRAFT_ORDER_CREATED/UPDATED`, three `FULFILLMENT_*` events since 2026-02-17 (3.23.0, #18809); `PRODUCT_VARIANT_DISCOUNTED_PRICE_UPDATED` 2026-03-31 (3.23.0, backported to 3.22.45); channel stock events 2026-04-21 (3.23.2, #19144). [L] — [#16999](https://github.com/saleor/saleor/pull/16999), [#18809](https://github.com/saleor/saleor/pull/18809)
- `FULFILLMENT_CREATED` and `FULFILLMENT_APPROVED` were flagged deferred on 2026-02-17 and reverted to inline on 2026-04-02 (#19011/#19012), six days before 3.23.0, because "Their subscribable object is a plain dict rather than a model … so it cannot be reconstructed in the task." [L] `88eee1d6b` — [#19011](https://github.com/saleor/saleor/pull/19011)
- Replica lag chain: "Retry webhook request in case EventDelivery cannot be found" (#17094, 2024-11-28, two weeks after deferred payloads landed) → "Wait for read replice before building deferred payload" (#18607, 2025-12-16) → reverted (#18635, 2025-12-18) → re-landed (#18638, 2025-12-23). The re-land PR says the first approach was reverted because "Aurora do not support some native PG methods"; the second checks that the delivery IDs are visible on the replica, wraps check + payload build in one transaction to pin a single replica, and converts the cooldown into SQS `DelaySeconds`. Tags 3.22.21 (12-17), 3.22.22 (12-18), 3.22.23 (12-22) bracket it. [L] `552024d04`, `ef3819df1`, `296b14445`, `ce3b63ede`; [W] — [#17094](https://github.com/saleor/saleor/pull/17094), [#18607](https://github.com/saleor/saleor/pull/18607), [#18635](https://github.com/saleor/saleor/pull/18635), [#18638](https://github.com/saleor/saleor/pull/18638)

### Inferences
- From 3.23 an app that applies order webhooks as an ordered event log is wrong by construction unless it sets `IMMEDIATE`; that option did not exist for roughly six months (2026-04-08 → 2026-10-16), and cannot be set by an app that must also install on cores older than 3.23.41 without a version gate in its manifest/webhook registration.
- Receivers must treat deliveries as at-least-once, possibly duplicated and state-at-read; core closed the duplicate-refund hole only by exposing a key the app must forward (core first, then app, and the app then requires the newer core).
- The primary database is the declared scaling bottleneck, so fixes that "just read from the writer" are rejected on principle; lag-tolerant designs (wait/retry) are preferred, and they depend on broker features (SQS delay, message groups).

### Gaps
- No public incident report describes which merchant integration broke on deferred order payloads; the ERP example is from the commit message only.
- The "sync webhook timeouts" default values and their history were not traced beyond #13989 (20 s for shipping filters).

## 4. Concurrency and ordering bugs (checkout completion, payments, stock, prices, metadata)

### Takeaway

### Inferences
- Races are fixed per mutation, so the same bug class survives in sibling mutations for months (TransactionEventReport → Create → Update → Initialize → Process → EventReport again).
- Several fixes ship with a data-repair step for rows already damaged (Atobarai payments migration, MPTT repair command, shared-address back-fill): the code fix alone does not heal live data, and the repair must run after the fix is live or it races with new damage.
- Adding a lock is frequently followed by a deadlock fix within weeks; lock *order* is the real invariant.
- Some fixes change the contract toward callers ("returns `TAX_ERROR` … Retrying the mutation succeeds"), so the dashboard/storefront must handle a new transient error.

### Gaps
- How each race was discovered (customer report, Sentry, load test) is not recorded in commit messages; issue links were not followed.
- No explicit "duplicate order" or "double charge" incident write-up was found; evidence is the fix titles and the duplicate-refund text in the Stripe app changelog (section 6).

## 6. Apps side: webhook migration on deploy, storage (APL) migration, SDK/API-version bumps, reinstall/reconfigure requirements

### Takeaway
Saleor apps are multi-tenant services whose state lives in three places (their own store, Saleor app metadata, and webhook registrations stored inside each tenant's Saleor), so every app release that changes a subscription query needs a per-tenant "webhook migration" run from the deploy script, and those scripts have themselves disabled webhooks, been reverted, and been version-sensitive. ### Inferences
- A webhook registration is data stored in *core's* database but owned and versioned by the *app*; an app deploy without the migration leaves old subscription queries live (old payload shape reaching new handler code), and a core upgrade that removes a field invalidates stored queries unless the app migrated them first. Order: app ships migration → runs across tenants → core removes the field.
- The app must tolerate tenants on several core versions simultaneously (manifest range `>=3.22 <4`), and codegen against the newest schema hides queries that older tenants reject; the failure is silent (webhook simply not registered).
- Per-transaction rows in the app's store record the core schema version at write time, so dropping support for an old core version is a data-compatibility change, not only a manifest change.
- HTTP status codes are a three-party protocol: for Saleor → app, 4xx = drop (and since 3.21 counts toward the breaker), 5xx = retry, 202 = "accepted but nothing done"; for Stripe → app, non-2xx = retry for up to three days and eventual endpoint disablement. Apps changed codes in both directions (500 → 400 to stop duplicate emails, 400 → 503 to stop lost emails, 400 → 202 to avoid the breaker, 400 → 200 for foreign Stripe events).

### Gaps
- From 2026-09-29 the public apps repo history consists of "Sync from internal repository (N changes)" commits with low PR numbers (#42, #76, #91, #150) while PRs two weeks earlier were numbered about #2443; individual changes after that date can only be cited via changelog entries, not PRs, and dates are approximate (Stripe 2.10.0 entry first appears in the sync commit of 2026-09-29).
- How tenant auth data was moved from the Saleor-Cloud APL to DynamoDB (a copy script, dual-read, or reinstall) was not found in the public repo.
- At HEAD, `apps/smtp/package.json` still points `migrate` at `./scripts/run-webhooks-migration.ts`, while the scripts directory contains `run-migration.ts` (the file was deleted in #2306). Observed in the clone; whether deploy uses that script was not checked.
- app-sdk repo itself was not examined.

## 7. Bugs diagnosed across owners (symptom in one system, cause in another)

### Takeaway
The clearest cross-owner cases are: missing emails caused by version skew in webhook registration or by status-code choice; duplicate refunds caused by core retries with no idempotency key; missing payment-method details caused by webhook/checkout-completion ordering; dashboard figures (`OVERCHARGED`, vanished variants, permission errors) caused by core semantics; and broken traces in apps caused by a core instrumentation change.

- Fix order was usually core first (expose a field or make an operation atomic), then app or dashboard, with the consumer then requiring the newer core or deliberately tolerating the older one.
