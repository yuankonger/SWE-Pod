## Which core API changes forced coordinated updates in several apps and the dashboard?

### Takeaway
Six change sets were found where three or more of core, dashboard, app-sdk and individual apps each needed their own non-trivial change against a shared contract. The three best are all "app platform" contracts from 2026 (App Problems; the identifier / OpenPopup / SEARCH_ACTION / RedirectToApp set; app deprecation with the SMTP sunset), and the widest business-flow one is payment-method details (core, Stripe app, NP Atobarai app, dashboard, SMTP app). In every one, the dependency is recorded mostly in changesets and commit bodies, and at least one intermediate state is documented as broken or silently inert.

### Cited Findings

#### Candidate C. App deprecation and the SMTP / Products Feed sunset (Sep to Oct 2026; core + app-sdk + dashboard + shared package + 3 apps)
- What: an app can mark itself deprecated; the dashboard warns at install and on installed apps and offers a "Migrate" link; the SMTP and Products Feed apps deprecate themselves on every existing installation.
- Core: `App.deprecationReason`, `Manifest.deprecationReason`, new `appSelfUpdate` mutation (`AUTHENTICATED_APP` only; staff `appUpdate` deliberately cannot set it; blank string clears, null/omitted leaves unchanged; over-long reasons truncated to 2048 characters). Merged 2026-09-30 into the `3.23` branch, port to main #19815, in release 3.23.38; 18 files +683/-2. ## Which business flows cross the most components, and which historical changes touched that whole chain?

### Takeaway
No single historical change touched the full checkout → tax → payment → order → email → refund → dashboard chain. The closest are payment-method details (payment app → core → dashboard → email, five components over 15 months) and App Problems (tax app and payment app both reporting into core and the dashboard). Cross-cutting compatibility changes ("drop 3.21", the 3.24 removal wave) touch every link at once but shallowly.
