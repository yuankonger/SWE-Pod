# Communication and social platforms split across several GitHub repos, as sources of cross-repo RL tasks

Method note (applies to everything below): on 2026-11-18 I made blobless, shallow clones (`--shallow-since=2025-12-01`) of 14 repos and read commit history, diff stats and file lists locally. Licences and last-push dates come from the GitHub REST API (`/repos/{o}/{r}`) and the raw LICENSE files. These repos squash-merge, so the PR number in each squash commit subject ("... (#1234)") gives a verified PR number and merge date (commit date). Zulip rebase-merges, so I looked up its PR numbers through the GitHub API `commits/{sha}/pulls`. Unauthenticated API quota ran out after those lookups, so PR-level totals for Zulip PRs (which span several commits) are missing. "Lines" below are `git show --shortstat` of the squash commit: insertions plus deletions. "testfiles" counts changed files that match test-path patterns. All dates are 2026 unless marked otherwise.

Repo URLs used as sources throughout: https://github.com/zulip/zulip, https://github.com/zulip/zulip-flutter, https://github.com/bluesky-social/atproto, https://github.com/bluesky-social/social-app, https://github.com/LemmyNet/lemmy, https://github.com/LemmyNet/lemmy-js-client, https://github.com/LemmyNet/lemmy-ui, https://github.com/matrix-org/matrix-js-sdk, https://github.com/element-hq/element-web, https://github.com/element-hq/synapse, https://github.com/mattermost/mattermost, https://github.com/mattermost/mattermost-mobile, https://github.com/jitsi/jitsi-meet, https://github.com/jitsi/lib-jitsi-meet

## Q1. Repos, languages and licences (LICENSE file / GitHub SPDX)

### Takeaway
Fully permissive multi-repo ecosystems are Zulip (all Apache-2.0), Bluesky (atproto MIT/Apache-2.0 dual + social-app MIT), Jitsi (jitsi-meet + lib-jitsi-meet Apache-2.0), the Matrix SDKs/spec (Apache-2.0) and Rocket.Chat outside `ee/` (MIT). Matrix's server and web client (Synapse, Element Web), Lemmy, Mastodon, Nextcloud, Element Call, Signal and Revolt/Stoat are AGPL-3.0, and Discourse is GPL-2.0. Mattermost is split: the server is AGPL with exceptions, while `webapp/` and mattermost-mobile are Apache-2.0.

### Inferences
- The AGPL's main extra obligation over the GPL is §13: if you modify the code and let users interact with it over a network, you must offer them the source. A private RL sandbox where only the training harness talks to the containers probably does not trigger distribution or §13 obligations. But the models' outputs are modified AGPL code, and some lab legal teams forbid AGPL code outright. Treat AGPL/GPL repos (Synapse, Element Web, Lemmy, Mastodon, Nextcloud, Signal, Discourse, Stoat, the Mattermost server) as "needs legal sign-off", not as hard-blocked. This is my reading, not legal advice.
- The safest fully permissive sets are: Zulip server + zulip-flutter; atproto + social-app; jitsi-meet + lib-jitsi-meet; matrix-js-sdk + matrix-rust-sdk + matrix-spec (without Synapse/Element); the Mattermost webapp half + mattermost-mobile (the Go server is AGPL).

### Gaps
- I did not read the licence files of python-zulip-api, zulip-desktop, zulip-terminal, element-x-ios/android, Rocket.Chat.ReactNative, the Mattermost plugins, or the Discourse official plugins.

## Q2. How the contract between repos is defined, and whether consumers vendor a copy

### Takeaway
Bluesky is the closest match to the Saleor pattern. Since Aug 2026 social-app vendors a copy of the atproto lexicon JSON (`lexicons/` + `lexicons.json`, checked in CI with `lex install --ci`), so a feature leaves a visible schema diff on both sides. Zulip's contract is the OpenAPI spec plus integer "feature levels". Lemmy's js-client consists of ts-rs types generated from the Rust backend. Matrix's contract is the spec + MSCs. Jitsi pins lib-jitsi-meet by release tarball URL. Mattermost-mobile hand-writes its client against the server REST API.

On 2026-11-19 server `version.py` has `API_FEATURE_LEVEL = 526` and `ZULIP_VERSION = "14.0-dev+git"`, and "API_FEATURE_LEVEL is bumped exclusively by tools/merge-api-changelogs" — [api_docs/changelog.md](https://github.com/zulip/zulip/blob/main/api_docs/changelog.md), [version.py](https://github.com/zulip/zulip/blob/main/version.py)

### Inferences
- For a Saleor-style "consumer keeps a copy of the provider's schema" contract, Bluesky (vendored lexicon JSON since Aug 2026) fits best. Lemmy is next: generated TS types are a copy of the Rust types, but they live in a third repo, so a task is backend + js-client + ui. Zulip's contract is semantic (OpenAPI YAML in the server + hand-written Dart models + feature-level gating). That is a good test of an agent writing feature-level-gated client code.
- For Matrix, the MSC is a natural written "contract" to hand agents as the task spec.

### Gaps
- I did not verify whether the Mattermost server's `server/public/model` Go types or an OpenAPI spec (mattermost/mattermost-api-reference) is consumed by mobile in generated form. Mobile appears to use a hand-written client.

## Q4. Test suites: framework, size, runnable offline in Docker, services

### Takeaway
All of these ecosystems have large server-side test suites that need a database (Postgres; plus Redis for atproto, Synapse optionally Postgres or SQLite). Client unit tests (Jest, Vitest, flutter_test, Karma) run offline. E2E suites (Maestro/Detox, Playwright/Cypress, WebdriverIO, Puppeteer) need simulators or browsers and should be excluded from hidden tests.

### Cited Findings
- Zulip server: `zerver/tests` has 149 `test_*.py` files and at least 4,473 `def test_` methods across zerver/tests + corporate/tests (my grep). The docs list suites "Linters, Django (… `test-backend`), Node (frontend JavaScript tests), Puppeteer (end-to-end UI tests in a Chromium browser)". The full backend suite runs "in under a minute on a fast laptop" (parallelised). Tests "must be run inside a Zulip development environment" — [Zulip testing docs](https://zulip.readthedocs.io/en/latest/testing/testing.html)
- zulip-flutter: 103 `*_test.dart` files under `test/` (flutter_test, uses `FakeApiConnection`, no server needed). 825 commits since 2026-01-01 — [zulip-flutter](https://github.com/zulip/zulip-flutter)
- atproto `packages/bsky` tests: `"test": "../dev-infra/with-test-redis-and-db.sh vitest run"`, i.e. they need Postgres + Redis. 83 `*.test.ts` files under packages/bsky/tests — [atproto bsky package.json](https://github.com/bluesky-social/atproto/blob/main/packages/bsky/package.json)
- social-app: Jest (`"test": "NODE_ENV=test jest --forceExit --testTimeout=20000 --bail"`), 225 `*.test.ts(x)` files. E2E uses Maestro (`"e2e:run": "maestro test"`) with iOS/Android builds — [social-app package.json](https://github.com/bluesky-social/social-app/blob/main/package.json)
- element-web: `"test:unit": "nx run-many -t test:unit:prepare -p && vitest run"`, 977 `*.test.ts(x)` files. matrix-js-sdk: 152 `*.spec.ts` files. synapse: 419 Python files under `tests/` (Twisted trial; SQLite by default, Postgres optional) — [element-web](https://github.com/element-hq/element-web), [matrix-js-sdk](https://github.com/matrix-org/matrix-js-sdk), [synapse](https://github.com/element-hq/synapse)
- Lemmy: about 295 `#[test]` / `#[tokio::test]` occurrences in .rs files (cargo test; DB tests need Postgres, per `scripts/test.sh`). `api_tests` are Jest federation tests (`jest -i --bail …`, follow/comment/post/community/… specs) that need several running Lemmy instances. lemmy-js-client has no test script (only build/lint/tsoa). lemmy-ui has `"test": "node --test \"src/**/*.test.ts\""` with only 1 test file — [lemmy api_tests/package.json](https://github.com/LemmyNet/lemmy/blob/main/api_tests/package.json), [lemmy-ui package.json](https://github.com/LemmyNet/lemmy-ui/blob/main/package.json)
- Mattermost: 1,016 `*_test.go` files in the monorepo (server tests need Postgres, among other things), 1,352 `webapp/**/*.test.ts(x)` files, and 758 `*.test.ts(x)` in mattermost-mobile (Jest) — [mattermost](https://github.com/mattermost/mattermost), [mattermost-mobile](https://github.com/mattermost/mattermost-mobile)
- jitsi-meet: `"test:unit": "vitest run"`, 103 `*.test|spec.ts(x)` files. lib-jitsi-meet: Karma (`"test:native": "karma start karma.conf.js"`, needs a headless browser), 82 test files — [jitsi-meet](https://github.com/jitsi/jitsi-meet), [lib-jitsi-meet](https://github.com/jitsi/lib-jitsi-meet)

### Inferences
- Easiest to containerise: Zulip, if you build the dev image with its provisioning script. Its fast backend suite plus offline flutter tests make server+mobile tasks cheap to grade. Bluesky (Postgres+Redis via dev-infra plus offline Jest) and Matrix (Synapse trial on SQLite plus offline Vitest/Jest) are also manageable.
- Lemmy is weak for hidden tests on the client sides (js-client has no tests and lemmy-ui has about one). Grading would rely on backend cargo tests plus type-checking ui/js-client against the generated types.
- Jitsi-meet feature PRs often add no unit tests (e.g. #17869, #18142). Lib-side PRs usually do.

### Gaps
- I did not measure actual Docker runtimes for any suite. Zulip's "under a minute" is the project's own claim for a fast laptop.
