# Build width, then make time bind

The next task should be a platform feature that one core contract forces on several independent consumers, not another bug fix. The best seed is Saleor's App Problems API: core, the dashboard, a shared package and four apps each needed their own non-trivial change, and the four app integrations landed on four separate days once the contract existed ([core #18724, opened](https://github.com/saleor/saleor/pull/18724), [apps #2255](https://github.com/saleor/apps/pull/2255)). Second is the mid-2026 set of stable identifiers and App Bridge actions, which is newer and deeper but needs a browser-level verifier. Third is a core upgrade run as a migration with a compatibility window, which is the seed where a deadline binds most naturally. Fourth is buyer-aware pricing, the only wide feature with no upstream answer to recall and the most expensive to build. The two-repository bug fix collapsed for a structural reason: a patch of about 100 lines sits in the size class frontier agents largely solve, and crossing a repository adds a lookup, not work ([RoadmapBench](https://arxiv.org/html/2605.15846v1)). Width alone will not make a team necessary, because no published study shows a team beating a solo agent on repository-scale coding at matched total tokens; the replicated team advantage is wall-clock time ([Co-Coder](https://arxiv.org/html/2606.00953v1), [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The task therefore needs a deadline or time-scored harm on a live system, plus conjunctive checks in every owner's territory. A company of five to seven owners can be assembled from BSD-3-Clause Saleor code alone, pinned to the 3.23 line, with Mailpit, a Stripe stand-in and an invented AvaTax stand-in. Nothing in this report was built or run, so every pin, size and ranking is a judgment from commit history and published benchmarks.

**How to read the links.** "Opened" in a link label means a researcher fetched that page. Other Saleor pull-request links were built from the number in a squash-commit subject in full-history local clones (core to 2026-11-12, dashboard to 2026-11-13, apps to 2026-10-28); the commit message and size were read and the web page was not. Sizes are `git show --shortstat` figures and include generated schema, codegen and lockfiles, so they overstate hand-written work. Since 2026-09-17 the public apps repository receives "Sync from internal repository" commits, so later app-side changes can only be cited by commit hash.

## A 100-line fix is solved; five joint sub-targets are not

The observed result (a mid-tier agent closing a two-repository bug fix in about 30 minutes for $2 to $5, from one repository) is what the size data predicts. Oracle patches run about 33 lines in SWE-bench Verified and 107 in SWE-bench Pro, against a median of about **3,700 lines over 51 files with five subtasks** in RoadmapBench, where the best agent resolves **39.1%** inside a two-hour limit ([RoadmapBench](https://arxiv.org/html/2605.15846v1)). Resolution there falls most clearly with files changed and with the number of sub-targets that must all pass; the best model's completion score is 0.692, so the "all must pass" rule does much of the work. FeatureBench tells the same story: a model at 74.4% on SWE-bench resolves 11.0% of feature-level tasks ([FeatureBench](https://arxiv.org/abs/2602.10975)). SaaSBench adds that integration, not logic, is the durable difficulty: best Pass@1 is 20.68%, and over 95% of failures occur before deep business logic because components never run stably together ([SaaSBench](https://arxiv.org/html/2605.17526)). Unsolved tasks in these suites consume a median of 7.6M and a mean of 27.2M tokens per rollout ([SWE-Marathon](https://arxiv.org/html/2606.07682)). A task that closes for $5 is too small by one to two orders of magnitude.

Size makes a task hard for one agent. It does not make several agents better. The nearest positive evidence is author-reported: Co-Coder, which splits work along dependency clusters, reaches 34.1% against 20.1% for a sequential agent on projects averaging 2,371 lines, 2.1 times faster and at lower cost, while naive file-based parallelism costs 1.4 to 1.6 times more for little gain ([Co-Coder](https://arxiv.org/html/2606.00953v1)). Anthropic's 16-agent compiler build worked while there were many distinct failing tests and stalled on one giant task, when "every agent would hit the same bug"; the fix was an external oracle that handed each agent a different failing file ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Where a solo reference with the same information exists, teams usually trail it: two parallel agents pass 16% and 57% of ParallACT's two instance types against 62% and 86% for one agent holding both requirements ([ParallACT](https://arxiv.org/html/2611.00314)).

Seven properties follow. The first three have direct support; the rest are synthesis from engineering practice and incident benchmarks.

| Property | What it requires | Why |
|---|---|---|
| Time binds | The serial sum of the work exceeds the window while the parallel critical path fits | Every positive team result found is a latency result, and 31.4% of agent-attributable failures on ultra-long tasks are timeouts ([SWE-Marathon](https://arxiv.org/html/2606.07682)) |
| Width with an interface | One shared contract and three or more independent consumers, each needing its own adaptation | Gains track dependency structure; width must come from real consumers, not from slicing one feature ([Co-Coder](https://arxiv.org/html/2606.00953v1)) |
| A per-unit oracle | Each owner can tell its own part is done without waiting for the others | Without one, parallel agents converge on the same bottleneck ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)) |
| Conjunctive scoring across owners | A producer obligation, one obligation per consumer and a system property, all required; partial completion reported separately | "Solved from one repository" means the checks could be met from one side |
| Both ends of expand and contract | Old clients work during the window; the old form is gone and fails loudly at the end | The pair rules out a producer-only shim and a consumer-only patch. Stripe's practice gives the checks: a recount with zero missing records, old and new reads compared before the switch, a hard error on the old path ([Stripe](https://stripe.com/blog/online-migrations)) |
| Live verification over time | Probes run through the whole change and continue after the agent says it is done | A symptom check is gamed: a restart loop passes 8 of 18 ITBench mitigation problems because the alert clears ([SREGym](https://arxiv.org/html/2605.07161v2)) |
| Private facts in runtime state | A fact that exists only in one service's stored data | A withheld requirement sentence is recoverable by a solo agent ([ParallACT](https://arxiv.org/html/2611.00314)) |

Incident tasks have their own measured levers. A second silent cause in another component takes success near zero even for a solo agent with full access, background noise costs 7 to 15 points, and novel faults score 15% to 28% against 63.7% for ported ones ([SREGym](https://arxiv.org/html/2605.07161v2)). No benchmark found scores harm integrated over time or forces triage across simultaneous incidents, so that design space is open. Because the comparison is a solo agent with all repositories, access partition cannot be the only source of necessity. Under full access the binding constraints are time and total work.

## Six Saleor change sets cross three or more components

A sweep of the clones found six change sets in which three or more of core, dashboard, app-sdk and individual apps each needed a non-trivial change against one contract. No single historical change touched the full checkout, tax, payment, order, email and refund chain.

| Seed | Components | Dates | Indicative size | Main strength | Main weakness |
|---|---|---|---|---|---|
| A. App Problems | core, dashboard, shared package, Stripe, CMS, AvaTax, Products Feed | Feb to Mar 2026 | core 30 files; dashboard 97 files; four apps add about 3,150 lines | Four parallel app integrations on one rule-rich contract | Public before mid-2026 |
| B. Identifiers and App Bridge actions | core, app-sdk, dashboard, AvaTax, Stripe, SMTP, onboarding | Jun to Aug 2026 | three core PRs of about 630 to 700 lines; eight dashboard PRs; seven app changes | Contract mismatches found only by the consumer | Outcome is mostly in the dashboard UI |
| C. App deprecation and SMTP sunset | core, app-sdk, dashboard, shared package, SMTP, Products Feed | Sep to Oct 2026 | core 18 files +683; dashboard 36 files +1,384; apps sync commit 125 files +3,469 | Rollout must reach already-installed apps | Replacement app is not public |
| D. Payment-method details | core, Stripe, NP Atobarai, dashboard, SMTP | Jun 2025 to Sep 2026 | core 22 files +3,026; Stripe 49 files; SMTP 6 files +149 | Longest business chain | Each hop is small and sequential; early hops public since 2025 |
| E. AppExtension redesign | core, dashboard, app-sdk | Jun 2025 to Sep 2026 | eight core PRs; dashboard 21 files +544/-439 | Real data migration and rollout order | Narrow; weak business outcome |
| F. 3.24 removal wave | core, dashboard, most apps, stored webhook queries | Jul to Sep 2026 | a dozen core removals; apps 28 files +578 for version checks | Very wide; compatibility is the whole task | Each part is shallow |

**App Problems (A) is the cleanest fit for width with an interface.** Apps report operational problems to core and the dashboard shows them with severity, count and dismissal. The contract carries rules each consumer must honour: aggregation by key within a sliding 60-minute window, a critical threshold, a cap of 100 problems per app with the oldest evicted, and dismissed problems excluded from aggregation ([core #18724, opened](https://github.com/saleor/saleor/pull/18724)). The Stripe integration alone touched five Saleor webhook handlers and the Stripe webhook handler in 36 files ([apps #2255](https://github.com/saleor/apps/pull/2255)); CMS, AvaTax and Products Feed followed separately ([apps #2260](https://github.com/saleor/apps/pull/2260), [apps #2261](https://github.com/saleor/apps/pull/2261), [apps #2265](https://github.com/saleor/apps/pull/2265)). The dependency is recorded in changesets, not links: the dashboard release "requires Saleor core 3.22.36. Used with older version, Extensions page will break" ([dashboard #6283, opened](https://github.com/saleor/saleor-dashboard/pull/6283)), and the apps needed a version gate that reads the Saleor version from the webhook payload, with one reporter dropped because its code path had no version ([apps commit 3146e805](https://github.com/saleor/apps/commit/3146e805)). The outcome is observable without reading code: break a Stripe key or AvaTax credential, place a checkout, and a problem appears, turns critical after repeats, and restarts its aggregate after dismissal.

**Identifiers and App Bridge actions (B) is the deepest negotiation.** The dashboard shipped ahead of both dependencies: its `identifier` field was "faked into the GraphQL schema until Saleor Core ships it; the action type is declared locally until @saleor/app-sdk does" ([dashboard #6667](https://github.com/saleor/saleor-dashboard/pull/6667)). A real mismatch surfaced only when the AvaTax app was built: OpenPopup resolves only popups registered on the current page, the command palette is not in that registry while closed, and no entity context is forwarded, so the app had to declare a second popup and pass the product id itself ([apps commit 179ff9d4](https://github.com/saleor/apps/commit/179ff9d4)). Consumers also had to stay compatible both ways: the onboarding app falls back when an older dashboard never acknowledges the redirect ([apps #2419](https://github.com/saleor/apps/pull/2419)), and the AvaTax action is gated on schema version instead of raising the required Saleor version, "which would drop 3.21/3.22 merchants" ([apps commit 90fdbc08](https://github.com/saleor/apps/commit/90fdbc08)). The business outcome exists (staff edit a tax code in the app popup, and the next checkout uses it) but most of the work is checked through iframes and popups.

**Deprecation (C) is a rollout seed layered on A.** An app marks itself deprecated through a new `appSelfUpdate` mutation because "manifests are only ever read at install time and apps are usually deprecated long after they are installed", and core surfaces the reason as a synthetic, non-dismissable App Problem ([core #19814, opened](https://github.com/saleor/saleor/pull/19814), [core commit 6c80157b1](https://github.com/saleor/saleor/commit/6c80157b1)). The app-side package must classify an older core as "unsupported" and a removed installation as "gone", and its cron sweep must finish within a time limit ([declare-app-deprecation.ts](https://github.com/saleor/apps/blob/main/packages/app-deprecation/src/declare-app-deprecation.ts), [apps commit 4400af60](https://github.com/saleor/apps/commit/4400af60)). A, B and C are layers of one platform, so a combined scenario is possible, but the Customer Emails replacement is absent from the public repository.

**Two unbuilt contracts have no upstream answer.** Buyer-aware pricing has a public eight-phase spec naming core, dashboard and apps, with no maintainer reply ([core #19380, opened](https://github.com/saleor/saleor/issues/19380)). Core's part exists on unmerged branches ending in a commit that freezes the API "so the dashboard can run its codegen against the schema" and records accepted gaps ([core commit ff828b838](https://github.com/saleor/saleor/commit/ff828b838)). No dashboard commit for scoped prices and no app commit mentioning customer types was found after that date. The app-side consequences (which price the feed publishes, what search indexes, whether a customer type maps to a tax exemption, what emails show) are this report's reasoning, not listed in any source. The smaller seed is per-webhook `payloadGeneration`: core and app-sdk 1.17.0 shipped it and no app has adopted it ([core #19916](https://github.com/saleor/saleor/pull/19916), [app-sdk releases, opened](https://github.com/saleor/app-sdk/releases)).

**The earlier incident seeds stay useful as overlays.** The double-refund chain remains the best case of enforced order: core had to expose an idempotency key in a specific patch, the Stripe app then consumed it, and the fix stayed inert until a per-installation migration rewrote the subscription query stored in core ([core #19811, opened](https://github.com/saleor/saleor/pull/19811), [apps #2446, opened](https://github.com/saleor/apps/issues/2446)). The SMTP case shows the same mechanism failing silently: a query selecting a 3.23-only type was rejected on 3.22, 7 of 9 webhooks failed to register, and the app sent no order emails ([apps #2442, opened](https://github.com/saleor/apps/pull/2442)). These are small in lines, which is why they fit one agent. They are strong as a concurrent obligation that arrives while a wide feature is in flight.

Older wide changes (the 2022 tax rework, the 2023 Transactions API, the 2023 email events) are large and well documented, and for that reason a model can recall them. Refund reasons is large but two-sided: no app commit mentions it.

**Owners.** Five to seven owners can come from first-party code alone, each mirroring a named repository or app directory: core API, dashboard, payments (Stripe app), tax (AvaTax app), notifications (SMTP app), catalogue distribution (CMS, search or Products Feed), and a platform owner holding `app-sdk` and the monorepo's shared `packages/`. The platform owner matters most for task design, because its changes cut across every app by construction. Core, dashboard and apps are BSD-3-Clause with CC-BY-4.0 artwork ([saleor LICENSE](https://github.com/saleor/saleor/blob/main/LICENSE), [dashboard LICENSE](https://github.com/saleor/saleor-dashboard/blob/main/LICENSE), [apps LICENSE](https://github.com/saleor/apps/blob/main/LICENSE)); app-sdk is BSD-3-Clause ([GitHub API](https://api.github.com/repos/saleor/app-sdk)). ## App Problems first, the upgrade window third, pricing last

The ranking weighs four things: separable work per owner, an outcome a hidden verifier can observe on the live company, exposure to recall, and build cost. It is a judgment; no agent has been run on any of these.

**1. App Problems across core, dashboard, the shared package and three or four apps.** It has the best width (one contract, four independent integrations with upstream references), the best per-unit oracle (each app's problem either appears in core or does not), and a verifier that needs no UI: inject a provider failure per app, then read `App.problems` and the dashboard's query. Each owner's obligation is separately checkable, including the rules a shallow implementation misses (window, threshold, cap of 100, dismissal). The idempotency or stored-query incident can be added as a page that arrives mid-task, with harm scored over time, so that serial handling costs points. That overlay is this report's synthesis. The risks are three. The feature has been public since February 2026 and is documented, so newer models can recall its shape. A strong solo agent may still finish it inside any generous window, since the contract is clear once written. And the 3.22.35 pin predates the 3.23 line that the current apps need, so the apps' version ranges at the February commit must be checked.

**2. Identifiers and App Bridge actions.** It is dated June to August 2026, spans four repositories, and contains the only recorded cases where a consumer discovered that the contract as built could not serve it. That is real negotiation. The risks are the verifier (popups, iframes and a command palette need browser automation, and a model judge should not gate the score), the strongly sequential chain from core to SDK to dashboard to app, and the app-sdk repository, which has not been cloned.

**3. A core upgrade run as a migration with a compatibility window.** Combine the 3.24 removals, `payloadGeneration` adoption and the AppExtension backfill, under live traffic. The checks come straight from migration practice: every app keeps all its webhooks registered, emails keep arriving in Mailpit, no dashboard screen fails, stored subscription queries are migrated per installation, and the removed fields fail loudly at the end. Upstream supplies the hazards: a backfill that "never runs if no worker picks it up" ([core commit ebe7c822e](https://github.com/saleor/saleor/commit/ebe7c822e)), stored queries that needed a per-installation migration script ([apps #2304](https://github.com/saleor/apps/pull/2304)), and a dashboard that kept selecting fields it assumed would stay deprecated ([dashboard #6871, opened](https://github.com/saleor/saleor-dashboard/pull/6871)). This is the seed where a deadline binds most naturally and where consumer count sets the width. The risks are that each part is shallow, so a solo agent grinds through it if the window is loose; that the harness must upgrade core under traffic; and that SMTP and Products Feed cap at `<3.24` with no public replacement, so the notifications owner has no upstream path forward.

**4. Buyer-aware pricing from the schema freeze.** It is the only wide and deep seed with a written contract and no upstream answer, and the dashboard and every app-side decision are unbuilt. The risks are the highest of the four: the benchmark must write and defend its own reference solution and verifier for each owner, the core branches are unmerged and of unknown authorship, and the public issue describes "customer tags" while the code uses customer types and attributes.

Payment-method details ranks below these. It has the longest business chain, but its hops are small, strictly sequential and months apart, and its early hops have been public since 2025. Deprecation is better used as a second phase of the first recommendation than alone.

**Admission.** Whichever seed is built, keep it only if a solo agent with all repositories at the same total budget fails or scores clearly lower inside the window, each single-owner-only attempt fails a named check, a no-messaging team does worse than a messaging team, and an agent told to cheat cannot pass. RoadmapBench had to repair 45 of 115 tasks after rollouts ([RoadmapBench](https://arxiv.org/html/2605.15846v1)), and 10.2% of long rollouts in SWE-Marathon shipped a clear verifier bypass ([SWE-Marathon](https://arxiv.org/html/2606.07682)). Probes and fault injectors must sit where no seat can read them; the known case of the payments seat reading sidecar files should be closed before runtime-private facts carry weight.

**Open questions.** The first group is about the build. Nothing was built, run or installed, so whether all components build and install at any listed pin is unknown, as are the memory and start-up cost of a stack with five or more Next.js apps. Whether a prerelease core such as `3.24.0-a.0` satisfies an app's `<3.24` range was not tested; semver ordering suggests it passes on the alpha and fails on the release. The second group is about licences: whether DynamoDB Local may be redistributed, whether dynalite runs the apps' access patterns, and what the licence file inside the Berkeley Objects archive says. The third is about the seeds: whether the `multi-dimensional-pricing-*` branches are maintainer work headed for main, whether the dashboard's webhook form supports `payloadGeneration`, and who negotiated what between repositories, since review threads were read for only four pull requests. The last is the one that decides the benchmark's claim: how tight the window must be for the solo and team ordering to flip. No controlled study varies a deadline, and no published verifier checks a compatibility window continuously during an agent-run migration.

## Conclusion

The research changes the question. "Which repositories must a fix touch" was the wrong axis: crossing a boundary is cheap for an agent that can read both sides. The axes that matter are how many independent consumers a contract has, how many obligations must hold at once, and whether the clock is part of the score. Saleor's app platform supplies the first two with real references. The third has to come from the harness, because upstream history records what was built, not how fast it had to be.

That also sets an honest expectation for the result. On current evidence a team will not beat a solo agent per token; it can finish inside a window the solo agent misses. If the first wide task still shows the solo agent winning at equal budget, the next lever is to shorten the window or add a concurrent incident, not to widen the feature further. The no-upstream-answer seeds are worth their cost only after that calibration exists.
